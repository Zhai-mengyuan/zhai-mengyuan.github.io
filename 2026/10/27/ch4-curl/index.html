curl 上手实录：从一条 GET 到上传、下载与证书边界

发表于2026-10-27|更新于2026-10-27|网络渗透测试课程博客
|浏览量:

本章作业要求（网络渗透测试 · 第四章：主动扫描）

第四章讲主动扫描——主机发现、端口扫描、系统与服务指纹、NMAP 与它的脚本。curl 不在这些工具之列，但它是同一件事的另一种做法：nmap 扫的是「哪个端口开着」，curl 问的是「开着的那个端口会说什么」。前者给你一张地图，后者让你站到门口敲一下门，听里面回话的口音。

本文按十步走一遍，每一步都附实拍输出和一句「这一行说明了什么」，最后汇总六个坑和一条防守视角。

全文区分两类陈述：实测（本文终端有直接输出）与推断（依据协议规范，文中标出）。

一、预备知识

1.1 HTTP 是一次「问答」

浏览器访问网页，本质是发一段文本、收一段文本：

服务器回：

curl 干的事就是把这两段文本原样打在你眼前——浏览器替你藏起来的东西，它全给你看。

1.2 常用参数：按用途分四组

用途 参数 说明
看响应 -I 只要响应头（HEAD 请求），不下载正文
-i 响应头 + 正文一起输出
-v 详细模式，连 TCP/TLS 握手和请求原文都打出来
控流程 -L 跟随 301/302 跳转（默认不跟）
-k 跳过证书校验（仅测试用）
--max-time N 超时上限，防止卡死
发数据 -X POST 指定请求方法
-d 请求体（默认表单，配合 -H 可发 JSON）
-F multipart 上传，file=@本地路径
存结果 -O 用远端文件名保存
-o 名字 自己指定保存名
-w 模板 按模板输出耗时等统计

1.3 状态码：先认这几类

段位 含义 例子
2xx 成功 200 OK
3xx 重定向 301 永久、302 临时
4xx 客户端错 403 拒绝、404 不存在
5xx 服务端错 500 内部错误、502 网关错误

主动扫描里，状态码本身就是情报：403 说明目录存在但不让看，404 说明没有，换成 200 就说明有东西。

二、实验环境

项目 说明
系统 Windows 11，PowerShell 5.1（管理员窗口）
工具 curl 8.21.0（Windows 自带），libcurl 8.21.0
TLS 后端 Schannel（走 Windows 系统证书库）
练习目录 D:\curl-test
测试目标 example.com / baidu.com / httpbin.org / badssl.com / github.com（全部公开站点）

全部实验只对公开站点发普通请求，不涉及任何未授权目标。文中截图里本机与出口地址已打码。

三、第一步：确认环境

输出信息比看上去多，逐项拆：

字段 含义
curl 8.21.0 (Windows) libcurl/8.21.0 命令行版本 + 底层库版本
Schannel TLS 后端用 Windows 自带的 SChannel，证书校验走系统证书库
zlib/1.3.2 支持压缩传输
WinIDN 支持国际化域名（中文域名）
WinLDAP 编进了 LDAP 协议支持
Protocols: 支持的 20 多种协议，http/https/ws/wss/ldap 都在
Features: HSTS、HTTPS-proxy、SSPI、SPNEGO、Unicode 等能力清单

为什么先看这一行：后面 -k 与证书报错的行为，都由 Schannel 这一项决定——它用的是系统证书库，所以自签名证书会被系统判为「不受信任」，与 curl 本身无关。

四、第二步：第一条 GET

终端刷出一整行 HTML：<!doctype html><html lang=en><head><meta charset=utf-8>...<title>Example Domain</title>...。

三个要点：

  • 默认 GET，不需要写 -X GET；
  • 输出的是源码，不是渲染后的页面——浏览器做的排版、执行 JS，curl 一概不做；
  • 正文里那句 This domain is for use in documentation examples without needing permission 说明它是专门给文档举例用的保留域名，拿它练手不会打扰任何真实站点。

五、第三步：只看响应头

输出只有头，没有正文。逐行读：

响应头 实测值 读出来的信息
状态行 HTTP/1.1 200 OK 走 HTTP/1.1，正常
Server bfe 百度自研接入层（Baidu Front End）——这一行就是指纹
Content-Type text/html 返回的是网页
Content-Length 0 HEAD 只问头，正文按规范不返回
Cache-Control private, no-cache, no-store, proxy-revalidate, no-transform 全禁缓存，说明这条路径是动态生成的
Pragma no-cache 给老 HTTP/1.0 代理看的同一意思
Set-Cookie BAIDUID=...; Max-Age=31536000、BAIDUID_BFESS=...; Secure; SameSite=None 下发一年期标识 Cookie，Secure 表示只走 HTTPS

防守视角的一句话：Server 头把接入层软件名直接告诉了对方。生产环境常见做法是把它改成 Server: nginx 之外的无意义值，或由反向代理统一覆写——减少指纹，就是增加对方的摸索成本。

六、第四步：-v 看一个请求的完整生命周期

-v 输出的每一行前面有符号，含义固定：

前缀 含义
* curl 自己的过程信息（连接、握手、耗时）
> 我发出去的请求
< 服务器回来的响应

按时间顺序拆解这段输出：

  1. * Trying 52.44.60.253:443... 与 * Trying 3.211.106.232:443... —— 一个域名解析出多个 A 记录，curl 依次尝试，第一个不通就换下一个（这也是排查「为什么连的是这个 IP」的依据）；
  2. * schannel: disabled automatic use of client certificate —— 没有客户端证书可发，跳过（访问双向认证站点时这里会不同）；
  3. * ALPN: curl offers http/1.1 / * ALPN: server accepted http/1.1 —— ALPN 是 TLS 握手时协商「接下来用什么应用层协议」，这里两边只谈成 http/1.1，没升到 h2；
  4. * Established connection to httpbin.org (52.44.60.253 port 443) from *** port 18693 —— 连接建立，括号里是服务端，from 后面是本机出口地址与临时端口（已打码）；
  5. > GET /get HTTP/1.1、> Host: httpbin.org、> User-Agent: curl/8.21.0、> Accept: */* —— 请求原文，UA 明晃晃写着 curl；
  6. < HTTP/1.1 200 OK 之后是响应头：Server: gunicorn/19.9.0（Python 的 WSGI 服务器，又是一条指纹）、Content-Type: application/json、Content-Length: 254、Access-Control-Allow-Origin: *（开放 CORS）；
  7. 最后 * Connection #0 to host httpbin.org:443 left intact —— 连接保留在连接池里，后续请求可复用（keep-alive）。

这一节的价值：以后任何「为什么请求失败」的问题，-v 都能定位到卡在哪一层——DNS？TCP？TLS？还是服务器回了 4xx。排错先分层，别一上来就猜。

七、第五步：301 与 -L

第一条输出很短：

301 是「永久搬家」，Location 告诉你去哪。curl 默认停在这里，不会自动跟——这是新人最容易误判的地方：明明浏览器打开是 200，脚本里却是 301。

第二条加了 -L，于是继续跟到 https://github.com/，拿到 200 OK 和一长串响应头。其中有几行值得注意：

  • Strict-Transport-Security: max-age=31536000; includeSubdomains; preload —— HSTS，告诉浏览器「以后这个域名只能走 HTTPS」；
  • 一大串 *.githubusercontent.com 出现在 Content-Security-Policy 里——CSP 白名单，说明这个站点允许从哪些域加载资源；
  • Server 段与普通站点不同（GitHub 前端用了自研/定制接入），X-GitHub-Request-Id 之类用于排障追踪。

把这些头连起来看，就能大致判断一个站点的技术栈与安全策略——这正是 whatweb 这类指纹工具自动做的事，curl 只是让你手工看见原始证据。

八、第六步：POST JSON

三个参数各管一件事：

  • -X POST：方法改成 POST；
  • -H "Content-Type: application/json"：告诉服务器「body 是 JSON」，不加这行，服务器会按表单解析；
  • -d '...'：请求体。

输出里能验证它真的收到了："json": {"id": 123, "name": "quanquan"}，Content-Length: 28 —— 28 字节正好是那段 JSON 的长度。

⚠️ PowerShell 里的引号是这一节最大的坑：外层用单引号，JSON 内部的双引号要转义成 \"。写成 '{"name":"x"}' 在 PowerShell 里会被拆成多个参数，报「意外的标记」。CMD 里则要写成 "{\"name\":\"x\"}"，两套规则不一样。

九、第七步：-F 上传文件

关键点：

  • @ 不能丢。-F "file=test.jpg" 传的是字符串 test.jpg，加 @ 才是「读这个文件」；
  • Content-Type: multipart/form-data; boundary=----CQx4HB3... —— 表单上传靠 boundary 分隔各字段，这串随机字符由 curl 自动生成；
  • 回显里 "files": {"file": "data:image/jpeg;base64,..."} —— 服务器认为这是一张 JPEG，因为文件名后缀是 .jpg。

最后这点是个现成的安全结论：echo demo 写进去的明明是文本（PowerShell 的 > 重定向按 UTF-16LE 存，所以内容只有十几个字节），但 MIME 类型照样被判定成 image/jpeg——因为客户端只给了文件名，服务端按后缀猜。现实中这就是「扩展名伪造」：把 webshell 改名成 .jpg 上传，只靠后缀校验的接口会放行。服务端校验必须看内容（魔数）而不是看名字。

十、第八步：下载与证书边界

第一条会打一张进度表（% Total、% Received、Average Speed 等），跑完当前目录多出 baidu.html——用 curl 抓页面存档，就是一条命令的事。

第二条和第三条是这个实验最有教学价值的一组对比：

  • 加 -k：200 OK，正常拿到页面；
  • 不加 -k：直接失败，

60 是 curl 的证书校验错误码，后半句由 Schannel（Windows 证书库）给出——这正是第三节 --version 里那个 Schannel 的落地表现。curl 没有自己判断证书合不合法，它把这件事交给了操作系统的证书信任链。

所以 -k 的真实含义是「关掉整个校验」：不仅跳过「证书过期」「域名不匹配」，也跳过「这是不是中间人」。它只该出现在靶场、自签名内网测试里；在生产脚本里出现 -k，等于把 HTTPS 退化成 HTTP。

十一、防守视角：主动扫描留下的痕迹

这一章是「主动扫描」，主动就意味着对方看得见。curl 的每个请求都会在服务端留下一条访问日志，里面至少包含：时间、来源 IP、路径、状态码、User-Agent、Referer。

攻击者常利用两点：

手法 原理 防守对策
改 UA 伪装浏览器 -A "Mozilla/5.0" 一行就能改，服务端看到的 UA 完全可伪造 别把 UA 当身份凭证；异常 UA 只作为风控信号之一
扩展名伪造上传 见第九节，MIME 由文件名推断 按魔数校验 + 重命名 + 上传目录禁止执行
绕过证书告警抓流量 客户端加 -k 或安装恶意根证书 终端做证书固定（pinning）、监控系统根证书变动

反过来，防守方也可以主动用 curl 做两件事：验证自己的响应头有没有多说话（比如 Server、X-Powered-By 是否暴露版本），以及验证证书链是否完整（不加 -k 能否成功）。

十二、命令速查

十三、踩坑记录

1. PowerShell 里的 curl 不是 curl。 curl 是 Invoke-WebRequest 的别名，参数体系完全不同，curl -I 会报「找不到与参数名称 I 匹配的参数」。写全名 curl.exe 才是真的 curl。同类陷阱还有 wget、ls、rm。

2. 在系统目录里写文件会被拒。 管理员窗口默认开在 C:\WINDOWS\System32，echo demo > test.jpg 直接报 UnauthorizedAccessException。先 cd D:\curl-test 再干活——-o 下载、-F 上传都受同一个影响。

3. JSON 的引号两套规则。 PowerShell 用 '{\"k\":\"v\"}'，CMD 用 "{\"k\":\"v\"}"，写反了服务器收到的是被截断的字符串。

4. -F 漏掉 @。 上传变成传字符串，服务器端只会看到一个叫 test.jpg 的文本字段。

5. curl: (56) schannel: server closed abruptly。 偶发，先换目标验证工具本身正常（换 baidu 或 httpbin），再判断是目标链路问题——分层排查，别怀疑命令写错。

6. 把 -k 当万能药。 它跳过的是整条信任链，包括中间人检测。生产环境永远不要出现。
