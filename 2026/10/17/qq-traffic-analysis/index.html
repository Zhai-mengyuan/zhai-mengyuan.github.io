用 Wireshark 分析 QQ 流量：TCP/UDP、加密方式与文件还原实测

发表于2026-10-17|更新于2026-10-25|网络渗透测试课程博客
|浏览量:

本章作业要求（网络渗透测试 · QQ 流量分析：PC-PC 端、PC-手机端）

本文回答三个问题：QQ 走 TCP 还是 UDP、流量是加密还是明文、能不能从流量里把传过的文件还原出来。答案是：以 TCP 为主（97.2%）、三层加密但明文留了破口、文件能不能拿到取决于走哪条通道——局域网直传（8082）和 httpconn 回落这两条路都是明文，剥掉几十到一千多字节的头就能拿到完整图片，本文两次实测都还原成功了。

三处需要重点看的地方：

  • 第四节「实测一」：手机 → 电脑，探到 QQ 的局域网直传端口 8082，2509 KB 的 TCP 流里剥掉 80 字节 HTTP 头还原出整张照片；
  • 第五节「实测二」：PC → 文件传输助手，httpconn 明文通道，剥掉 1,365 字节私有协议头还原出 1280×1707 的原图；
  • 第九、十节（步骤 4、5）：为什么很多人照着范文抓不到东西——TLS 通道上 7 种特征码零命中，得先把加密边界搞清楚；

全文区分两种陈述：实测（本文实验有直接输出，附帧数或命令）与推断（依据协议规范或实现原理，文中会标出）。

二、预备知识

2.1 TCP/IP 四层模型

层 职责 典型协议 本实验关心的内容
应用层 面向具体业务 HTTP、DNS、FTP、TLS 能不能读出内容
传输层 端到端通信、端口寻址 TCP、UDP 用哪个协议、端口号
网际层 跨网络寻址与路由 IP、ICMP 源 IP、目的 IP
网络接口层 同一链路上的帧传输 以太网、Wi-Fi MAC 地址、帧长

分层的作用是解耦：应用层不需要知道底层用 Wi-Fi 还是以太网，网络接口层也不关心上层传的是聊天记录还是图片。

2.2 TCP 与 UDP

特性 TCP UDP
连接 需三次握手建立 无连接，直接发送
可靠性 确认、重传、按序交付 不保证送达，不保证顺序
开销 头部 20 字节起，有状态 头部 8 字节，无状态
典型用途 网页、文件、聊天 DNS、视频、游戏、QUIC

TCP 三次握手：

TCP 为了保证顺序，必须等前一个包确认后才能交付后面的数据。如果中间丢了一个包，后续包即使已到达也要排队等重传，这叫队头阻塞。这是后来 QUIC 改用 UDP 的主要原因。

2.3 端口

端口是 16 位整数，范围 0–65535，用于区分同一台主机上的不同进程。

范围 名称 说明
0–1023 知名端口 系统服务，需特权
1024–49151 注册端口 常见应用
49152–65535 动态端口 客户端临时使用

常见知名端口：

端口 服务 端口 服务
21 FTP 443 HTTPS

23 Telnet 3306 MySQL
25 SMTP 3389 RDP

扫描和流量分析都要靠端口判断服务类型，但要注意：端口可以改，判断服务最终还是要看协议特征。

2.4 加密基础与 TLS

两类加密：

类型 代表算法 特点 用途
对称加密 AES、ChaCha20 快，但密钥分发困难 加密实际数据
非对称加密 RSA、ECC 慢，可安全交换密钥 密钥协商、签名

TLS 用的是混合加密：

证书的作用常被忽略：没有证书，攻击者可以中间人转发双方密钥，加密照样成立，但中间人能看到全部内容。证书解决的是”你在跟谁加密”的问题。

TLS 1.3 相比 1.2 的主要改进：握手从 2-RTT 降到 1-RTT、支持 0-RTT 恢复、废弃了不安全的 RSA 密钥交换、加密了更多握手字段。

2.5 SNI：加密握手中的明文

一台服务器可能托管上百个网站，客户端必须在握手时告诉服务器”我要访问哪个域名”，这个字段就是 SNI（Server Name Indication）。

问题在于：TLS 1.2 的 SNI 是明文传输的，TLS 1.3 默认也仍是明文（除非启用 ECH）。

所以即使内容全加密，中间人依然能看到你访问了哪些域名。这是本文第四步能读出 beacon.qq.com 这类域名的原因。

2.6 QUIC 与 HTTP/3

QUIC 是 HTTP/3 的底层协议，跑在 UDP 上，但自己实现了可靠传输。

它解决的是 TCP 的三个痛点：

  • 队头阻塞：多路复用，各数据流独立重传，互不阻塞；
  • 握手延迟：内建 TLS 1.3，首次 1-RTT，恢复连接 0-RTT；
  • 连接迁移：用连接 ID 而不是四元组标识连接，手机从 Wi-Fi 切到 4G 时连接不断。

QUIC 在协议层强制加密，因此抓包只能看到握手和密文。

2.7 DNS 为什么是明文的

DNS 设计于 1983 年，当时没有加密的考虑，且基于 UDP 53 端口，追求轻量和低延迟。

明文带来两个问题：

  • 可监听：谁都能知道你查了哪些域名；
  • 可篡改：DNS 劫持、投毒由此产生。

对策是 DoH（DNS over HTTPS）、DoT（DNS over TLS）、DoQ（DNS over QUIC），把查询塞进加密通道。目前系统默认仍多为明文 DNS，因此本文的抓包里域名清晰可见。

三、复现流程

步骤 操作 预期结果
1 列出网卡并抓包 90 秒 生成 pcap 文件
2 统计协议分布 TCP 占 90% 以上，各协议帧数之和 = 总帧数
3 定位 QQ 长连接 找到长期 ESTABLISHED 连接，载荷含心跳报文
4 提取 TLS SNI 出现 qq.com / tencent.com 域名
5 按文件特征码搜索 TLS 通道合计仅 2 帧命中且都在密文里；若命中落在 80 端口的 httpconn，则是真明文（见第五节）
6 对照实验：明文 HTTP 传输 文件被完整还原，MD5 一致

如果抓包期间发过图片，建议在六步之外再加一步：按第五节从 httpconn 通道导出，看能不能还原。

四、实测一：手机 → 电脑传图还原

4.1 手机 → 电脑：完整实测（含截图）

本次方向是手机发图给电脑（手机端 QQ 发送，电脑端接收），全程在校园网 GUET-WiFi 下进行。工具：QQ、Wireshark、010 Editor。

1. 保证两端处于同一网络。 电脑与手机都登录 QQ，并连接同一个 WiFi。这是整个实验的前提——不同网段之间走的是公网中转。

实测两端拿到的都是 10.34.x.x 内网地址：手机 10.34.10.228，电脑 10.34.1.70。注意两者不在同一个 /24 网段（10.34.10.228 与 10.34.1.70），说明这是学校出口路由下的不同子网，中间隔着三层设备——所以不能假设手机和电脑之间能直接二层通信。但能通信 ≠ 要同网段：只要路由能通、NAT 没挡住，QQ 就有机会建立局域网直传（见第 5 步）。

2. 选择 WiFi 网卡开始抓包。 打开 Wireshark，选 WLAN 接口开始捕获。

3. 确认两端的 IP 地址。 手机 WiFi 设置里看当前分配的内网 IP，电脑用 ipconfig 查——两边都要有，后续判断流量方向全靠它。

4. 过滤出目标流量。 本次实际命中流量的过滤器是这条（端口 8082，见第 5 步说明）：

这张图信息量很大，值得细读：

  • 第 942 号帧就是整件事的开端——手机发了一条 GET /qfile?re=…&rhpath=…&eflag=…&token=…&fileSize=…&filename=…&range=… HTTP/1.1，请求行本身就写在明文里，文件名、文件大小、range 全都看得见；
  • 随后 948–954 号帧是手机（10.34.10.228）对电脑（10.34.1.70）连续回 [TCP Previous segment not captured] 的 ACK，中间缺了序号段——说明电脑正在往手机发数据时，你这台机器只抓到了手机这一侧（因为你说抓包网卡选的是本机 WLAN，而这条流的对端是本机 8082 服务，方向和截图里的 10.34.1.70→10.34.10.228 说明数据是电脑发给手机的）；
  • 协议列写着 HTTP，一眼就能确认这条通道没加密。

⚠️ 注意：如果要发的图片在电脑上已经存在（QQ 之前传过），传输时会直接走「秒传/引用」，真实数据根本不经过网卡，这种情况抓不到图片。无论接收方是手机还是好友的电脑都一样——发之前把图片换个文件名另存一份，或现场拍一张新照片，保证它对 QQ 来说是「新文件」。

5. 定位承载图片的那条 TCP 流。 本次的关键发现是端口 8082：

项目 实测值
客户端（手机） 10.34.10.228:58150
服务端（电脑） 10.34.1.70:8082
协议 HTTP/1.1（明文）
流量 2509 KB

8082 是 QQ 的局域网直传通道——两端在同一网络时，QQ 不走腾讯服务器中转，而是直接在自己机器上开一个本地 HTTP 服务，让对端来拉文件。这正是「同一 WiFi 才能抓到明文」的原因：一旦跨网，这条通道建立不起来，就只能走 TLS 加密的服务器中转。

流量 2509 KB 也说明这是一张不小的图，值得一挖。

6. 追踪 TCP 流，切到原始数据。 右键任意一条该流的报文 → 追踪流 → TCP（不是 HTTP）。本次这条流里虽然有 HTTP/1.1 200 OK 的响应头，但右键里选 TCP 流才拿得到完整的原始字节；随后把「显示为 ASCII」改为「显示原始数据」。

原始数据里能直接看到 ...JFIF........、...Exif..MM.、...Adobe 这些字样——明文 JPEG 就在眼前。

7. 导出为图片文件。 点窗口右下角「另存为…」，存成 复原.jpg。此时双击打不开：

8. 用 010 Editor 定位多余字节。 打开 复原.jpg，文件开头是这样的：

文件开头多了 80 字节的 HTTP 响应头：HTTP/1.1 200 OK、Server: QQ/1.0 (Tencent)、Content-Length: 20956、Connection: keep-alive，以两个 0D 0A（空行）结束。真正的 JPEG 从偏移 0x50（即 80 字节处） 的 FF D8 FF E1 开始——FF D8 是 JPEG 的 SOI 标记，FF E1 是紧跟的 APP1（EXIF）段。

9. 删掉多余字节并保存。 把 FF D8 之前的 80 字节全部删掉（010 Editor 里选中 0 到 0x4F，删除），保存。

10. 重新打开。 图片成功还原：

一张 2509 KB 的 TCP 流，剥掉 80 字节 HTTP 头，得到的 JPEG 完全可读——同一 WiFi 下的 QQ 传图既没加密、也没做额外封装，只是套了个 HTTP 响应头。

4.2 本场景的三个结论

问题 结论
UDP 还是 TCP 抓到的图片流量是 HTTP，HTTP 基于 TCP，因此属于 TCP
加密还是明文 图片数据以明文形式出现在 HTTP 响应体中，未加密，原始数据里能直接看到图片内容
能否恢复明文文件 能。HTTP 流里的图片是「裸」数据，开头缺少标准文件头；不同类型各有特征码（JPEG 是 FF D8），删掉前面的多余字节即可正常打开

这三条在下面的手机→电脑实测中全部得到验证，且比第五节更彻底：第五节是 PC→「文件传输助手」（本机自发自收），本次是两台真实设备跨子网传输，结果是 2509 KB 的 TCP 流里剥掉 80 字节 HTTP 头，直接得到完整 JPEG。

值得注意的是两条路径的开销差了一个数量级：

路径 场景 需要剥掉的封装 实测
httpconn 通道 PC → 文件传输助手 1,390 字节（含私有协议头） 第五节，158,920 → 157,530 字节
局域网直传 8082 手机 → 电脑 80 字节（纯 HTTP 响应头） 第四节，2509 KB 流还原成功

局域网直传的封装更薄——因为它本来就是「我开个 HTTP 服务，你来 GET」这种最朴素的方式，没有 QQ 私有协议那一层。两端在同一网络时，QQ 反而会选这条最不加密、也最容易还原的路。

这也解释了为什么很多人按范文做不出来：如果两端不在同一网络（手机走流量、或校园网开了 AP 隔离导致直传失败），QQ 就会回落到腾讯服务器中转，走的是 TLS 加密通道，自然什么都抓不到。 这两条路径必须分清：

局域网直传（实测一） 服务器中转
触发条件 两端同网络且能互通 跨网、NAT 不通、直传失败
端口 本地随机开一个（本次 8082） 443（TLS）、80（httpconn）
加密 无 TLS 加密 / httpconn 明文回落
能否还原 能 TLS 不能；httpconn 能

若要与 PC→PC 对照，需要两台电脑同时抓包，并按实测一的方法在两端分别定位流、导出还原。

4.3 背景：PC-PC 与 PC-手机的一般情况

项目 PC → PC PC → 手机
测试对象 好友的电脑 自己的手机
传输路径 优先 P2P 直连，失败转服务器中转 一般经服务器中转
端口特征 高位随机端口直连 + 控制信道 443（TLS）与 80（httpconn 明文）都可能
加密情况 推断为加密 聊天内容加密，但图片走 httpconn 时是明文（第五节实测的是 PC→「文件传输助手」，走的就是明文 httpconn）

先交代场景边界：第五节的还原实验是 PC→「文件传输助手」（PC 端自发自收，消息不出本机与服务器之间），它证实的是明文 httpconn 通道本身能还原文件；「文件传输助手」不等于 PC→手机——真正的手机端收图要用手机登录 QQ 接收，收图时的手机侧流量也要抓。下面给出同一 WiFi 下的完整对照实验流程，把 PC→手机真正落到实机上。

五、实测二：httpconn 通道的图片还原（PC → 文件传输助手）

前面所有结论都建立在一个前提上——文件走的是 TLS。但 QQ 还有一条明文 HTTP 通道：当 TCP 直连不通、或走特定业务（比如发图）时，客户端会退回 http://htdata3.qq.com/cgi-bin/httpconn?htcmd=...&uin=...，把文件直接塞进 POST body。

脚本不想写也可以用 010 Editor 手动剥，三步：

① 跳到图片开头：Ctrl + G 跳转到偏移 1365（即 0x555），核对光标处显示 FF D8 FF E0 00 10 4A 46 49 46——4A 46 49 46 就是 ASCII 的 JFIF，看到它说明站对位置了。

② 选中到图片结尾：菜单 编辑 → 选择 → 选择范围，起始地址填 1365、长度填 157530（= 158,894 − 1,365 + 1，正好是图片的完整大小）。嫌对话框麻烦也可以手动点选：点一下 1365 处的 FF，Ctrl + G 跳到 158,894，按住 Shift 点一下结尾的 FF D9，状态栏显示选中 157,530 字节即对。

踩坑记录：选择范围对话框左下角有个进制开关（Hex / Dec）。如果在 Hex 模式下填十进制的 157530，会被解析成 0x157530 ≈ 140 万字节，直接报「选择是以前文件的结尾」。两套数值对号入座：

对话框模式 起始地址 长度
十进制（Dec） 1365 157530
十六进制（Hex） 0x555 0x2675A

用「跳转 + Shift 点选」则完全不涉及进制换算，比填对话框稳。

这条实验把「TLS 通道零命中」的结论限定了范围：「QQ 传的文件不可还原」只在 TLS 通道成立。控制面与聊天内容确实加密，但图片一旦落到 httpconn 通道就是明文——URL 里带着 uin，body 里躺着能直接查看的 JPEG。

7.1 数字必须对得上

统计结果加不回总数，说明口径不一致。本次核对：

项 帧数 说明
TCP 51,876 含控制帧与数据帧
UDP 1,471 承载的 UDP
ICMP 23 其中 16 条为目的不可达差错

有两个容易算错的地方。

一、用过滤器数出的 UDP 是 1,487，不是 1,471。

多出的 16 帧是 ICMP 目的不可达报文——差错报文的载荷里嵌了触发它的原始 UDP 头，于是同时被 udp 过滤器命中。

过滤器的命中数不等于独立事件数。 涉及 ICMP 差错、隧道封装时，同一帧可能被多个协议过滤器重复计数，只有协议分级（-z io,phs）的统计是按帧去重的。

二、TCP 的 51,876 帧里只有一部分带数据。

类型 帧数 占比
无载荷（SYN / ACK / FIN） 21,438 41.3%
有载荷 30,438 58.7%

有载荷的帧中，21,442 帧被解析出应用层协议（TLS 20,367 + data 1,069 + http 6），其余 8,996 帧是 Wireshark 标为 “TCP segment of a reassembled PDU” 的分片，不单独计入应用层。所以协议树里 TLS 等协议之和远小于 TCP 总数，这是正常的。

三、data 不等于「QQ 私有协议」。

协议树里那 1,069 帧 data 是 Wireshark 没解析出应用层协议的载荷，不是某个具体协议。按端口拆开看：

所在端口 帧数 实际是什么
443 1,050 中途加入抓包、快速重传或握手后未被解析的 TLS 段
7402 / 14000 17 QQ 主链路的私有协议载荷

也就是说，只有这 17 帧属于 QQ 的私有协议，8.2 分析心跳用的就是它们。把 data 整段当作私有协议会高估 QQ 的流量。

7.2 协议树里多出来的 vlan 层

本机抓包中有 31,332 帧（58.7%）带 802.1Q 标签，且 VLAN ID 全为 0。这不是 VLAN 划分，而是无线网卡驱动为 QoS 插入的优先级标签（priority tag）。

Wireshark 会把它画成一个独立的 vlan 分支，导致同一个 ip 节点出现两次、各层数字看起来对不上。处理办法：把两个 ip 分支相加（本文做法）。

它只影响协议树的分支统计，不影响 tcp contains、ip.addr 这类按内容或地址的过滤——那些过滤器看的是帧里的字节，与有没有 802.1Q 标签无关。

图形界面对应「统计 → 协议分级」，适合截图。

8.1 用 netstat 找服务端

没有 SYN，说明连接在抓包开始前就已建立；没有 FIN / RST，说明 90 秒窗口内没有断开。这就是长连接，不是每条消息单独建连。

端口不固定。 实测中见过 14000、443、80 等不同端口，随版本与网络环境变化。判断长连接的依据不是端口号，而是两点：连接长期保持 ESTABLISHED，且载荷中存在心跳报文。

9.2 五条通道的加密方式

通道 端口 协议 可见内容
消息主链路 TCP 14000（本次观察） 腾讯私有二进制协议 协议头明文，内容密文

前四条通道里，只有 DNS 的查询内容完全明文；但第五条是真正的例外——QQ 在部分场景下会把图片走明文 HTTP，URL 带 uin，body 可还原。这也是本文最需要说清楚的一点：「QQ 全加密」这个说法不成立。

还有一个例外：抓包里有 6 帧 HTTP 请求行是明文的（微信的 mmtls 外层），见第十二节。

9.3 加密的边界

  • 内容：消息与 TLS 通道上的文件加密，第三方无法读取；但走 httpconn 通道的图片是明文，可直接还原（见第五节）；
  • 元数据：DNS 域名、TLS SNI、连接时刻（明文时间戳）、流量大小，均可观察。

仅凭元数据就能知道「几点上线」，再推测「用了哪些功能、传了多大的文件」。进一步，包大小分布与时序还能区分文字、图片、语音，这类分析称为流量指纹。

加密保护内容，不保护行为，也不完全保护身份。这是当前加密协议的共同边界，也是 DoH、ECH 这类技术要解决的问题。

FF D8 FF 只有 3 字节，在数千万字节的密文中出现两次属正常概率。可靠识别要把特征码延长：正常 JPEG 紧跟 FF D8 之后是 FF E0（JFIF）或 FF E1（EXIF），可用 FF D8 FF E0 / FF D8 FF E1 检索。

换句话说，3 字节特征码对密文几乎没有区分力，只适合在明文流量里做粗筛；命中只说明「可能有」，不说明「找到了」。

十二、其他观察

12.1 两处局域网明文

一、一条直发本机的 UDP。

要注意它不是广播：目的 IP 是本机地址，目的 MAC 也是本机网卡，属于单播。全网只有这一个包，没有回应，像是某台设备在探测局域网内的服务。

二、4 条 SSDP。

SSDP 是即插即用设备的发现协议，这 4 条是本机主动发出的搜索请求（M-SEARCH），同样是明文。

对比可见：面向公网的应用普遍加密，局域网发现类协议多数还是明文。内网流量的可见性远高于公网。

12.2 一个「假明文」：微信的 mmtls

协议树里那 6 帧 http 乍看像明文 HTTP，实际长这样：

请求行、Host、路径、状态码都是明文，可以直接读；报文正文则是 mmtls 加密的，内容不可读。所以能看出「本机在跟微信通信」，看不出「通信了什么」。

3 条请求中，后 2 条的 Host 直接写成了 IP（120.233.23.125、120.241.131.24:8080），路径同样是 /mmtls/xxxx；另外 3 帧是对应的响应。

这也说明：抓包里出现微信流量，不代表 QQ 用了明文，而是本机同时在跑微信。取样时只盯 14000 端口，很容易漏掉这类「看起来是 HTTP」的帧。

十三、隐私处理

信息类型 是否可见 来源
聊天内容 不可见 走 TLS / 私有协议，内容密文

行为与偏好 可推断 流量大小、时序、访问的域名
网络出口地址 可见 IP 头

QQ 号本身也是明文，这一点最反直觉。 用 frame contains "你的QQ号" 就能直接搜到：本文 17 分钟的抓包命中 80 帧，另一次 90 秒的抓包命中 11 帧。它们出现在两个地方：

  • HTTP 连接通道：QQ 在 TCP 直连失败或特定场景下回落到 HTTP，请求行形如 GET /cgi-bin/httpconn?htcmd=0x6ff0082&uin=1234567890 HTTP/1.1（host 为 htdata3.qq.com 等）——uin 就写在 URL 参数里，完全明文；
  • 私有协议的头部：443 端口上跑的并不都是 TLS，QQ 私有协议的报文头里，从固定偏移（本文观测为第 14 字节起）开始就是 uin 的 ASCII 十进制字符串，后接密文体。Wireshark 按 443 端口把它误标成 SSL，所以这些帧显示为 “Continuation Data”，内容却搜得到。

也就是说，加密保护的是聊天内容，不保护你是谁。这也解释了为什么第一份抓包（90 秒、QQ 空闲）里一帧都没命中——httpconn 通道不是每次都走，搜不到不代表不存在。

若要把 pcap 交给别人（交作业、发帖），先用这条过滤器找出所有含 uin 的帧，导出前脱敏或只给过滤后的统计结果。

发布前的处理：

  • 本机地址一律写作「本机」，同网段其他设备写作 10.34.102.x；
  • 昵称、好友信息不含；QQ 号的处理见下一条；
  • 腾讯服务器 IP 保留（公开信息，无隐私风险）；
  • 本文截图中的 QQ 号、本机 IP 与 MAC 没有打码——一是因为号码在包里本来就是明文，打码反而遮住了实验的重点；二是这是自己的博客。如果你要把同样的截图交作业或发到别的平台，建议先打码再发；
  • pcap 里若含图片传输，先按第五节检查能不能还原——能还原就必须把这段流量剔除，或者干脆不交原始包。

域名清单是本文最容易被忽略的一项，但还不是最严重的。 49 个域名里，云盘、浏览器、办公软件各自留痕，从域名能反推出这台机器装了什么、在用哪些服务，所以正文只列出与 QQ 相关的 13 个。比域名更要紧的是图片：一旦走 httpconn，原图就躺在包里，导出即可查看——交作业前务必确认 pcap 里没有别人发给你、或你发给别人的照片。
