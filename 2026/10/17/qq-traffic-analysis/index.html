用 Wireshark 分析 QQ 流量：TCP/UDP、加密方式与文件还原实测

发表于2026-10-17|更新于2026-10-20|课程笔记
|浏览量:

课程要求分析自己日常使用的 QQ：它走 TCP 还是 UDP、流量是加密还是明文、能否从流量中还原传输的文件。

本文分三部分：先补齐分析所需的协议基础，再按实验步骤给出可复现的操作与预期结果，最后给一张自检表，用来判断自己跑出来的结果是否正确。

结论

问题 结论 依据
UDP 还是 TCP 以 TCP 为主，占 97.2% 53,376 帧中 TCP 51,876 帧，UDP 1,471 帧（2.8%）
加密还是明文 加密（私有协议 + TLS + QUIC 三层） 应用数据不可读；明文只有 DNS/SNI、心跳元数据与 HTTP 请求行——但 QQ 号就藏在这些明文里，见第十三节
文件能否还原 分通道：图片能还原，TLS 通道的内容不能 图片走 httpconn 明文通道，私有头 + 裸 JPEG，偏移 1,365 起可直接抠出；TLS 通道上 7 种特征码零命中

全文区分两种陈述：

  • 实测：在本次抓包中有直接证据，附帧数或命令输出；
  • 推断：依据协议规范或实现原理得出，本次未单独验证，文中会明确标出。

第三行结论是分通道的，读的时候别把它压成一句话：聊天内容和 TLS 通道里的文件确实拿不到，但图片走 httpconn 回落时是明文 HTTP，body 里就是一张能直接打开的 JPEG（8.4 有完整还原过程）。

数值来自两次 90 秒抓包：第一次 53,376 帧，第二次只有 1,992 帧，TCP 占比都是 97.2%，也都搜得到心跳报文。包的数量能差上百倍，协议构成却稳定——这本身就是判断自己抓得对不对的依据。

二、预备知识

2.1 TCP/IP 四层模型

层 职责 典型协议 本实验关心的内容
应用层 面向具体业务 HTTP、DNS、FTP、TLS 能不能读出内容
传输层 端到端通信、端口寻址 TCP、UDP 用哪个协议、端口号
网际层 跨网络寻址与路由 IP、ICMP 源 IP、目的 IP
网络接口层 同一链路上的帧传输 以太网、Wi-Fi MAC 地址、帧长

分层的作用是解耦：应用层不需要知道底层用 Wi-Fi 还是以太网，网络接口层也不关心上层传的是聊天记录还是图片。

2.2 数据封装与 PDU

数据从应用层往下走，每层加一个头部，这个过程叫封装；接收端逐层剥掉头部叫解封装。

因此同一个请求在 Wireshark 里能看到四层信息，这也是判断协议结构的基础：头部通常是明文，载荷才是业务数据。

2.3 TCP 与 UDP

特性 TCP UDP
连接 需三次握手建立 无连接，直接发送
可靠性 确认、重传、按序交付 不保证送达，不保证顺序
开销 头部 20 字节起，有状态 头部 8 字节，无状态
典型用途 网页、文件、聊天 DNS、视频、游戏、QUIC

TCP 三次握手：

TCP 为了保证顺序，必须等前一个包确认后才能交付后面的数据。如果中间丢了一个包，后续包即使已到达也要排队等重传，这叫队头阻塞。这是后来 QUIC 改用 UDP 的主要原因。

2.4 端口

端口是 16 位整数，范围 0–65535，用于区分同一台主机上的不同进程。

范围 名称 说明
0–1023 知名端口 系统服务，需特权
1024–49151 注册端口 常见应用
49152–65535 动态端口 客户端临时使用

常见知名端口：

端口 服务 端口 服务
21 FTP 443 HTTPS
22 SSH 1433 SQL Server
23 Telnet 3306 MySQL
25 SMTP 3389 RDP
53 DNS 6379 Redis

扫描和流量分析都要靠端口判断服务类型，但要注意：端口可以改，判断服务最终还是要看协议特征。

2.5 加密基础与 TLS

两类加密：

类型 代表算法 特点 用途
对称加密 AES、ChaCha20 快，但密钥分发困难 加密实际数据
非对称加密 RSA、ECC 慢，可安全交换密钥 密钥协商、签名

TLS 用的是混合加密：

证书的作用常被忽略：没有证书，攻击者可以中间人转发双方密钥，加密照样成立，但中间人能看到全部内容。证书解决的是”你在跟谁加密”的问题。

TLS 1.3 相比 1.2 的主要改进：握手从 2-RTT 降到 1-RTT、支持 0-RTT 恢复、废弃了不安全的 RSA 密钥交换、加密了更多握手字段。

2.6 SNI：加密握手中的明文

一台服务器可能托管上百个网站，客户端必须在握手时告诉服务器”我要访问哪个域名”，这个字段就是 SNI（Server Name Indication）。

问题在于：TLS 1.2 的 SNI 是明文传输的，TLS 1.3 默认也仍是明文（除非启用 ECH）。

所以即使内容全加密，中间人依然能看到你访问了哪些域名。这是本文第四步能读出 beacon.qq.com 这类域名的原因。

2.7 QUIC 与 HTTP/3

QUIC 是 HTTP/3 的底层协议，跑在 UDP 上，但自己实现了可靠传输。

它解决的是 TCP 的三个痛点：

  • 队头阻塞：多路复用，各数据流独立重传，互不阻塞；
  • 握手延迟：内建 TLS 1.3，首次 1-RTT，恢复连接 0-RTT；
  • 连接迁移：用连接 ID 而不是四元组标识连接，手机从 Wi-Fi 切到 4G 时连接不断。

QUIC 在协议层强制加密，因此抓包只能看到握手和密文。

2.8 DNS 为什么是明文的

DNS 设计于 1983 年，当时没有加密的考虑，且基于 UDP 53 端口，追求轻量和低延迟。

明文带来两个问题：

  • 可监听：谁都能知道你查了哪些域名；
  • 可篡改：DNS 劫持、投毒由此产生。

对策是 DoH（DNS over HTTPS）、DoT（DNS over TLS）、DoQ（DNS over QUIC），把查询塞进加密通道。目前系统默认仍多为明文 DNS，因此本文的抓包里域名清晰可见。

2.10 Wireshark 的抓包原理

Wireshark 通过 libpcap / Npcap 调用网卡驱动，把经过网卡的帧复制一份。

两个容易混淆的概念：

捕获过滤器（BPF） 显示过滤器
生效时机 抓包时 抓完之后
语法 tcp port 443 tcp.port == 443
作用 减少写入量，丢掉的包无法恢复 只影响显示，数据仍在文件里

本文用的都是显示过滤器，因为需要保留全量数据做统计。

还有一个常见误解需要澄清：在交换式网络中，网卡只能收到发往本机的单播帧和广播帧。 想看到其他设备的流量，需要 ARP 欺骗或交换机端口镜像。所以本文所有数据均来自本机，结论也只对本机成立。

三、复现流程

步骤 操作 预期结果
1 列出网卡并抓包 90 秒 生成 pcap 文件
2 统计协议分布 TCP 占 90% 以上，各协议帧数之和 = 总帧数
3 定位 QQ 长连接 找到长期 ESTABLISHED 连接，载荷含心跳报文
4 提取 TLS SNI 出现 qq.com / tencent.com 域名
5 按文件特征码搜索 TLS 通道合计仅 2 帧命中且都在密文里；若命中落在 80 端口的 httpconn，则是真明文（见 8.4）
6 对照实验：明文 HTTP 传输 文件被完整还原，MD5 一致

六步跑完后，用第十一节的自检表逐项核对。如果抓包期间发过图片，建议再加一步：按 8.4 从 httpconn 通道导出，看能不能还原。

五、步骤 2：统计协议分布

输出（已合并 VLAN 分支，节选）：

观察点：

  • TCP 占绝对多数（97.2%）；
  • UDP 只有 1,471 帧，主要被 QUIC（1,250 帧）与 DNS（210 帧）占用，不承载聊天消息；
  • 应用层 TLS 有 20,367 帧，说明大量流量在加密通道内。
  • 另有 3 帧走 IPv6 的 mDNS（ff02::fb:5353），不在上面的 IPv4 分支里，但已计入 UDP 的 1,471 帧。

5.1 数字必须对得上

统计结果加不回总数，说明口径不一致。本次核对：

项 帧数 说明
TCP 51,876 含控制帧与数据帧
UDP 1,471 承载的 UDP
ICMP 23 其中 16 条为目的不可达差错
ARP 6 地址解析
合计 53,376 与总帧数一致

有两个容易算错的地方。

一、用过滤器数出的 UDP 是 1,487，不是 1,471。

多出的 16 帧是 ICMP 目的不可达报文——差错报文的载荷里嵌了触发它的原始 UDP 头，于是同时被 udp 过滤器命中。

过滤器的命中数不等于独立事件数。 涉及 ICMP 差错、隧道封装时，同一帧可能被多个协议过滤器重复计数，只有协议分级（-z io,phs）的统计是按帧去重的。

二、TCP 的 51,876 帧里只有一部分带数据。

类型 帧数 占比
无载荷（SYN / ACK / FIN） 21,438 41.3%
有载荷 30,438 58.7%

有载荷的帧中，21,442 帧被解析出应用层协议（TLS 20,367 + data 1,069 + http 6），其余 8,996 帧是 Wireshark 标为 “TCP segment of a reassembled PDU” 的分片，不单独计入应用层。所以协议树里 TLS 等协议之和远小于 TCP 总数，这是正常的。

三、data 不等于「QQ 私有协议」。

协议树里那 1,069 帧 data 是 Wireshark 没解析出应用层协议的载荷，不是某个具体协议。按端口拆开看：

所在端口 帧数 实际是什么
443 1,050 中途加入抓包、快速重传或握手后未被解析的 TLS 段
7402 / 14000 17 QQ 主链路的私有协议载荷

也就是说，只有这 17 帧属于 QQ 的私有协议，第 6.2 节分析心跳用的就是它们。把 data 整段当作私有协议会高估 QQ 的流量。

5.2 协议树里多出来的 vlan 层

本机抓包中有 31,332 帧（58.7%）带 802.1Q 标签，且 VLAN ID 全为 0。这不是 VLAN 划分，而是无线网卡驱动为 QoS 插入的优先级标签（priority tag）。

Wireshark 会把它画成一个独立的 vlan 分支，导致同一个 ip 节点出现两次、各层数字看起来对不上。处理办法：把两个 ip 分支相加（本文做法）。

它只影响协议树的分支统计，不影响 tcp contains、ip.addr 这类按内容或地址的过滤——那些过滤器看的是帧里的字节，与有没有 802.1Q 标签无关。

图形界面对应「统计 → 协议分级」，适合截图。

没有 SYN，说明连接在抓包开始前就已建立；没有 FIN / RST，说明 90 秒窗口内没有断开。这就是长连接，不是每条消息单独建连。

端口不固定。 实测中见过 14000、443、80 等不同端口，随版本与网络环境变化。判断长连接的依据不是端口号，而是两点：连接长期保持 ESTABLISHED，且载荷中存在心跳报文。

七、步骤 4：判断是否加密

7.1 提取 TLS 的 SNI

顺带看握手的版本分布：

SNI 是明文，所以中间设备能知道本机访问了哪些服务，但读不到内容。

7.2 五条通道的加密方式

通道 端口 协议 可见内容
消息主链路 TCP 14000（本次观察） 腾讯私有二进制协议 协议头明文，内容密文
Web 与遥测 TCP 443 TLS 1.2 / 1.3 仅 SNI 域名
加速传输 UDP 443 QUIC 全密文
域名解析 UDP 53 DNS 明文域名
图片 / 文件（httpconn 回落） TCP 80（也见过 443） 明文 HTTP + 私有头 uin、文件名与文件本体，见 8.4

前四条通道里，只有 DNS 的查询内容完全明文；但第五条是真正的例外——QQ 在部分场景下会把图片走明文 HTTP，URL 带 uin，body 可还原。这也是本文最需要说清楚的一点：「QQ 全加密」这个说法不成立。

还有一个例外：抓包里有 6 帧 HTTP 请求行是明文的（微信的 mmtls 外层），见第十二节。

7.3 加密的边界

  • 内容：消息与 TLS 通道上的文件加密，第三方无法读取；但走 httpconn 通道的图片是明文，可直接还原（见 8.4）；
  • 元数据：DNS 域名、TLS SNI、连接时刻（明文时间戳）、流量大小，均可观察。

仅凭元数据就能知道「几点上线」，再推测「用了哪些功能、传了多大的文件」。进一步，包大小分布与时序还能区分文字、图片、语音，这类分析称为流量指纹。

加密保护内容，不保护行为，也不完全保护身份。这是当前加密协议的共同边界，也是 DoH、ECH 这类技术要解决的问题。

十二、其他观察

12.1 两处局域网明文

一、一条直发本机的 UDP。

要注意它不是广播：目的 IP 是本机地址，目的 MAC 也是本机网卡，属于单播。全网只有这一个包，没有回应，像是某台设备在探测局域网内的服务。

二、4 条 SSDP。

SSDP 是即插即用设备的发现协议，这 4 条是本机主动发出的搜索请求（M-SEARCH），同样是明文。

对比可见：面向公网的应用普遍加密，局域网发现类协议多数还是明文。内网流量的可见性远高于公网。

12.2 一个「假明文」：微信的 mmtls

协议树里那 6 帧 http 乍看像明文 HTTP，实际长这样：

请求行、Host、路径、状态码都是明文，可以直接读；报文正文则是 mmtls 加密的，内容不可读。所以能看出「本机在跟微信通信」，看不出「通信了什么」。

3 条请求中，后 2 条的 Host 直接写成了 IP（120.233.23.125、120.241.131.24:8080），路径同样是 /mmtls/xxxx；另外 3 帧是对应的响应。

这也说明：抓包里出现微信流量，不代表 QQ 用了明文，而是本机同时在跑微信。取样时只盯 14000 端口，很容易漏掉这类「看起来是 HTTP」的帧。

QQ 号本身也是明文，这一点最反直觉。 用 frame contains "你的QQ号" 就能直接搜到：本文 17 分钟的抓包命中 80 帧，另一次 90 秒的抓包命中 11 帧。它们出现在两个地方：

  • HTTP 连接通道：QQ 在 TCP 直连失败或特定场景下回落到 HTTP，请求行形如 GET /cgi-bin/httpconn?htcmd=0x6ff0082&uin=1234567890 HTTP/1.1（host 为 htdata3.qq.com 等）——uin 就写在 URL 参数里，完全明文；
  • 私有协议的头部：443 端口上跑的并不都是 TLS，QQ 私有协议的报文头里，从固定偏移（本文观测为第 14 字节起）开始就是 uin 的 ASCII 十进制字符串，后接密文体。Wireshark 按 443 端口把它误标成 SSL，所以这些帧显示为 “Continuation Data”，内容却搜得到。

也就是说，加密保护的是聊天内容，不保护你是谁。这也解释了为什么第一份抓包（90 秒、QQ 空闲）里一帧都没命中——httpconn 通道不是每次都走，搜不到不代表不存在。

发布前的处理：

  • 本机地址一律写作「本机」，同网段其他设备写作 10.34.102.x；
  • 不含 QQ 号、昵称、好友信息；
  • 腾讯服务器 IP 保留（公开信息，无隐私风险）；
  • 本文截图中的 QQ 号、本机 IP 与 MAC 没有打码——一是因为号码在包里本来就是明文，打码反而遮住了实验的重点；二是这是自己的博客。如果你要把同样的截图交作业或发到别的平台，建议先打码再发；
  • pcap 里若含图片传输，先按 8.4 检查能不能还原——能还原就必须把这段流量剔除，或者干脆不交原始包。

域名清单是本文最容易被忽略的一项，但还不是最严重的。 49 个域名里，云盘、浏览器、办公软件各自留痕，从域名能反推出这台机器装了什么、在用哪些服务，所以正文只列出与 QQ 相关的 13 个。比域名更要紧的是图片：一旦走 httpconn，原图就躺在包里，导出即可查看——交作业前务必确认 pcap 里没有别人发给你、或你发给别人的照片。

十四、踩坑记录

1. PowerShell 脚本中文乱码

.ps1 文件若不带 BOM，Windows PowerShell 5.1 会按系统 GBK 编码解析，UTF-8 中文变成乱码并导致语法错误。

解决：保存为 UTF-8 with BOM。

2. PowerShell 里的 curl 不是 curl

PowerShell 5.1 把 curl 别名指向 Invoke-WebRequest，参数体系完全不同，curl -o 文件 会直接报参数错误。

解决：写全名 curl.exe（Windows 10 1803 起自带），或改用 Invoke-WebRequest -OutFile。同一类陷阱还有 wget、ls、rm，在 PowerShell 里都指向了别的命令。

3. 中文路径导致 objdump 失败

解决：把文件复制到纯英文路径再分析。

4. 特征码假阳性

FF D8 FF 命中 2 帧，一度以为「QQ 传了未加密的图片」，核查后发现位于 TLS 密文中。

教训：命中后必须逐帧确认，不能只看计数；短特征码要配合上下文校验。

5. 过滤器计数与总帧数对不上

按协议逐个过滤再相加，结果比总帧数多出十几帧（本文是 UDP 多 16 帧）。

原因：ICMP 差错报文的载荷里嵌了原始 UDP 头，导致同一帧被两个协议过滤器各计一次。要按帧去重，用 -z io,phs，不要手加过滤器结果，详见 5.1。

6. dumpcap -D 的网卡名是乱码

cmd 默认代码页是 GBK，而 dumpcap 输出的是 UTF-8，于是「本地连接」显示成 鏈湴杩炴帴 这样的乱码。不影响功能——编号照样能用，WLAN、Loopback 这类英文名也认得出来。想看清中文名，先执行 chcp 65001 再运行，或直接改用 Windows Terminal。

7. 在 cmd 里敲 PowerShell 命令

Measure-Object、Get-FileHash、Get-NetTCPConnection、$pids = (Get-Process QQ).Id 这些全是 PowerShell 的语法。在 cmd 里执行会得到两种结果：要么 'xxx' 不是内部或外部命令，要么更隐蔽——命令被拆成几段，每段各报一次「命令语法不正确」，看起来像命令写错了，其实是解释器不对。

判断方法：提示符是 C:\Users\xxx> 就是 cmd，是 PS C:\Users\xxx> 才是 PowerShell。在 cmd 里敲一句 powershell 就能切过去，exit 退回。

同理，D:\test 目录不存在时 dumpcap -w D:\test\http_demo.pcapng 会报 could not be opened: No such file or directory——dumpcap 不会替你建目录，先 mkdir D:\test 再抓。

网络渗透测试课程第一次课后作业，也是这个博客的第一篇文章。开博客一半是课程要求，一半是我自己想找个地方把学的东西写成文字——光会做不等于会讲，写出来的过程就是把知识真正过一遍脑子。平时的输出过程很少导致一些知识很容易模糊忘记，不能光输入不输出啊。 一、先补一块地基：CIA 三要素聊等保之前，得先弄明白”安全”到底在保护什么。信息安全领域最经典的模型叫 CIA 三要素（跟中央情报局没关系，是三个单词的首字母）： 机密性（Confidentiality）：只有被授权的人或程序，才能访问和查看数据。（保护数据内容不能泄露，加密是是实现机密性要求的常见手段） 完整性（Integrity）：数据保持正确、完整的状态，不能被未授权地修改——无论篡改是意外还是恶意。（常见的保证一致性的技术手段是数字签名） 可用性（Availability）：被授权的人需要用数据的时候，系统随时能用。 CSO Online 的一篇经典文章（见文末参考 1）用银行 ATM 机举例：银行卡 + 密码的双重认证保证机密性；转账金额准确入账、账户余额不被算错，保证完整性；机器 24 小时分布在街头、银行下班了也...
