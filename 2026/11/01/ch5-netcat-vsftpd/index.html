NetCat 与笑脸后门：从端口到 root 的六步

一、完成笑脸漏洞检测 PoC（Python 即可），源码截图、测试过程记入 blog。

二、小组讨论完成皮卡丘靶场搭建（个人开始尝试通关）：皮卡丘靶场（Pikachu）是专为 Web 安全初学者设计的中文漏洞练习平台，源码托管在 GitHub 上，覆盖暴力破解、XSS、SQL 注入等数十种常见 Web 漏洞场景，能让你在本地可控环境中系统练习渗透测试基础技能。过程记入 blog。

三、高阶要求：通过分析源码，总结漏洞成因，如何修复？

作业一共三项：本文做第一项（Python PoC）和第三项（源码成因与修复）；第二项的皮卡丘靶场是小组任务，单独写一篇，不混在这里。

第五章讲漏洞扫描。课件前半段是方法论：什么样的东西算漏洞，怎么从端口和版本号里把它认出来；后半段是一串工具名字——Nmap、OpenVAS、ZAP。夹在中间的是 NetCat，一个 1996 年就有的老东西，没有图形界面，参数还得背。

但这一章真正要动手的地方，恰恰是这个老东西。漏洞扫描的链条其实只有三环：发现一个口子 → 判定它是什么 → 证明它真能被用。前两环 Nmap 干得比谁都漂亮，第三环得靠一个能把字节亲手送出去的通道。

这一篇就走这条链的第三环，六步：扫端口 → 抓 banner → 建连接 → 传文件 → 拿 shell → 触发笑脸后门拿 root。中间会踩一个必踩的坑：书上的 nc 和你机器上的 nc 可能不是同一个程序。第九节是作业要的 Python PoC，第十节回到源码看成因与修复。

一、预备知识

1.1 NetCat 到底是个什么

课本 P121 叫它「网络工具中的老前辈」。这个称呼不算夸奖，是陈述事实——它 1996 年就有了，比大多数人接触网络的时间都早。

它的功能一句话能说完：把 TCP/UDP 连接的两头，接到两个文件描述符上。一头是 socket，一头是 stdin/stdout。于是它能干的事就取决于你怎么接：

接法 效果
stdin/stdout ↔ socket 手打文字发出去（聊天、抓 banner）
本地文件 ↔ socket 传文件
一个程序 ↔ socket 把程序的输入输出挂到网线上，这就是 -e

后面五步全是这一句话的排列组合。所以它被叫「瑞士军刀」——不是因为它功能多，是因为它只有一个刀片，但什么都能拧。

1.2 三个必认的参数

参数 作用 哪一步会用
-n 不做 DNS 反解，直接认 IP 全程（不写会卡在域名解析上）
-v / -vv 输出连接过程，-vv 更详细 第一次连某端口时看状态
-z 零 I/O，只做 TCP 握手，连上就断 扫端口

-z 值得单说。它不是「发个包试试」，是真的完成一次三次握手再主动关掉。所以 open 意味着对端确实有程序在 listen，Connection refused 意味着主机活着但那个端口没人接——后者反而是好消息，说明网络是通的，只是服务没开。

顺带一句：不同版本的 nc 措辞不一样，传统版说 open，openbsd 版说 succeeded!。意思完全相同，看到哪个都别以为装错了。

1.3 漏洞扫描在扫什么

课件 P9–P11 用 vsftpd 2.3.4 做例子，这个例子的结构非常典型：

  1. 一个版本号就够了。FTP 服务连上来第一句话是 220 (vsFTPd 2.3.4)，服务端主动报出自己的名字和版本。攻击者不用猜、不用爆破，只要知道「2.3.4 这个版本有问题」。
  2. 问题大到不需要技巧。这个版本的后门不要求密码、不要求权限，只要用户名里带一个 :)。
  3. 结果直接是 root。不是普通用户，不是 ftp 用户，是 root。

所以第六步要证明的其实是一件很小的事：这行 banner 不是装饰，它是一份漏洞清单的目录。

三、第一步：扫端口

-w2 是每个端口等 2 秒，1-200 是范围。这条命令会刷一屏 Connection refused，中间夹着几个 open——要的就是那几个。

实测结果，200 个端口里开着 8 个：

端口 服务 意味着什么

25 smtp 邮件服务
53 domain DNS
80 http Web 服务
111 sunrpc RPC，Metasploitable2 上 NFS 相关漏洞的入口
139 netbios-ssn Samba 共享，usermap_script 一类漏洞的入口

这张截图只截到 1–35 号这一段，能看见 21、22、23、25 四个；53、80、111、139 在后面，滚上去才看得到。但这一段已经够看出规律了：Connection refused 和 open 交替出现，正好能对比两种状态。

这份表比它看起来信息量大。八个开着的服务，等于八份待查的版本号。这一篇只查 21 号，剩下的七个每一个都能单独写一章——139 的 Samba、111 的 NFS、23 的 telnet，都是 Metasploitable2 故意留的口子。

另外注意命令最后那行 sent 0, rcvd 0。这是 -z 的正常表现：只握手，不发数据，所以字节数是 0。第一次看到容易以为失败，其实恰恰说明它按设计工作了。

每行的格式也值得拆一下：(UNKNOWN) [192.168.96.129] 21 (ftp) open。

  • (UNKNOWN)：因为加了 -n 不做反向解析，所以没有主机名可显示。去掉 -n 这里会显示主机名（前提是网络里有 DNS 能解析），代价是每个端口都多等一次查询，扫 200 个端口会慢一大截。
  • [192.168.96.129]：方括号里才是 IP。
  • (ftp)：这是本地 /etc/services 里 21 号对应的服务名，nc 顺手查了一下表，不代表它真的验证了对面跑的是 ftp。想让工具真正识别服务，得上 Nmap 的 -sV。

开两个终端标签（Ctrl+Shift+T）。

这一步没有任何技巧，但它解释了后面所有事：TCP 只要一方占住端口、另一方连上来，两条 stdin/stdout 就接通了。中间那条线不关心跑的是文字、文件还是一个 shell 的输出——它只搬字节。

-l 是 listen，-p 指定端口。回环地址 127.0.0.1 表示自己连自己，不经过网卡，也就不用管防火墙。

5.1 连上之后，你敲的一切都是数据

这里有个几乎人人都会踩一次的地方，值得单独说。

图上在 nc -nv 127.0.0.1 4444 连上之后，接着敲了 nc -l -p 6666 -e /bin/bash、nc -nv 127.0.0.1 6666、whoami、id——四行一条都没执行。

原因很朴素：此刻终端 B 的 stdin 已经交给 nc 了，没有任何 shell 在解析你敲的东西。每一个回车只是把一行文字送过网线，落到对端的屏幕上。

想执行这些命令，先 Ctrl+C 退出当前会话，看到 $ 提示符回来，再重新敲。

这个坑在后面会以另一种形式再出现一次：只要 nc 没退出，你的键盘就不属于 shell。

这一步的现实意义比看上去大。nc 传文件不走认证、不加密、不留日志，所以在真实渗透里它常被用来「把工具送上去」或者「把数据带出来」。

qfbsz 是终端 A 那个用户的名字。也就是说，B 里敲的命令，是由 A 那边的 bash 执行的——B 拿到了 A 的 shell。

这一步要说清楚两件事，不然容易误会：

  1. 这不是漏洞，是我自己给自己开的门。 A 和 B 都是我的机器，-e 是我主动加的参数。它的价值是让人亲手摸一次「EXP 长什么样」，而不是「我攻破了谁」。
  2. 连上之后没有 $ 提示符是正常的。 因为 bash 是非交互启动的，不打印提示符。看不到提示符不代表没连上，直接敲命令就行——这一条我卡了一会儿。

把 -e 换个程序，就是另一种「服务」。-e /bin/sh 是 shell，-e /usr/bin/python3 是一个 Python 解释器，-e /bin/cat 是把对方发来的东西原样吐回去。后门的本质就是把某个程序的 stdin/stdout 接到网线上，而不是什么高深的技术。

八、第六步：笑脸后门，一步到 root

前面五步都是在自己机器上搭积木。这一步把积木搬到真靶场上。

8.1 触发

这条命令干了三件事：printf 拼出两行 FTP 协议文本、通过管道喂给 nc、nc 把它们发到 21 端口。\r\n 是 FTP 协议要求的行尾，少一个 \r 服务端会认不出来。

用户名是 hello:)——冒号加右括号，就是全部的利用条件。

-w 2 不能省。不加的话 nc 发完会一直挂着等对端回话，输出顺序会乱，看起来像卡死。

连上去先收到 banner，发完命令又收到一行：

331 是「用户名收到，请给密码」。它认认真真走了一遍登录流程，完全不知道自己刚才已经把后门打开了。 这一点很值得记：后门不是在「出错」的时候触发的，是在正常处理命令的时候顺手触发的，所以从服务端角度看，这次登录毫无异常。

8.2 别把三条命令糊在一起

-w 2 那句话说完，还是得看看「糊在一起」具体会出什么事，有张现成的反例图：

printf ... | nc 21 后面紧跟着粘了 sleep 2、nc -nv ... 6200、whoami 三行。结果是：FTP 只回了 220 和 331，6200 压根没被连接。

因为 nc 这时候还在等 stdin 关闭，你输入的每一行都被当成「要发给 FTP 的数据」送出去了。对 FTP 服务器来说，它收到了一个用户名、一个密码，然后收到一串莫名其妙的命令，最后 nc 因为没人关 stdin 一直挂着——-w 2 的意义就在这儿：给它一个「发完就收手」的期限。

正确做法是等 331 回来、$ 提示符重新出现，再单独敲下一条。

前面六步都是「人手工做一遍」。作业①要求把它变成脚本——换个人、换台机器、换一天，能不能一键得到同样的结论。

9.4 为什么不一上来就用脚本

写完脚本回头想，前面手敲的那几步没白花。脚本能自动化「已知的流程」，但发现不了「未知的异常」。比如第五步那个「-e 之后没有提示符」，手敲时会愣一下、然后试着敲 whoami；如果一开始就写脚本，这个细节会被 sleep(1) 悄悄吞掉，我永远不会知道那里出过问题。

十、高阶：源码里那段不属于 vsftpd 的代码

作业第三条要求「分析源码，总结成因」。这一步挖下去，会比前面所有步骤加起来更有意思。

10.1 后门不是一个 bug，是一段被塞进去的代码

正常的漏洞是「写错了」——缓冲区没检查长度、权限没校验。而 vsftpd 2.3.4 不是。它是一个功能完好的 FTP 服务，外加一段谁都不认识的代码。

事情的经过是这样的：2011 年夏天，vsftpd 发布 2.3.4 的源码包。紧接着作者就发现文件被人动过手脚（发布出去供下载的那份被替换了），紧急下架重发，版本号升到 2.3.5。被篡改的那份 vsftpd-2.3.4.tar.gz 里，多了一个函数。

所以严格说，这不是 vsftpd 的代码写出了 bug，是一次供应链投毒——攻击者没在代码里找漏洞，而是把发布出来的源码包换掉了。

10.2 触发点：两个字节的比较

被塞进去的代码分布在两处。

第一处在 str.c 的 vsf_cmdio_get_cmd_and_arg() 函数里，也就是处理 FTP 命令和参数的地方。公开流传的那份被篡改源码里，多出来的是这样一段判断：

0x3a 是 :，0x29 是 )。这段代码只做一件事：在收到的命令里找 :) 这两个相邻的字节，找到就调用 vsf_sysutil_extra()。

放到上下文里看，i 扫的是整条命令的缓冲区，所以不需要精确构造——只要在用户名里带上 :)，这两个字节就会出现在缓冲区里，判断就成立了。这就是为什么 USER hello:) 能触发，而 USER hello 不能。

10.3 后门本体：一个只做六件事的循环

第二处在 sysutil.c 里的 vsf_sysutil_extra()。这个名字起得极有心机：直译是「额外的系统工具」，和旁边一堆 vsf_sysutil_* 混在一起毫不显眼，内容却是一个完整的独立后门服务端。公开流传的那份源码，结构是六步：

这六步和第五节那条 nc -l -p 6666 -e /bin/bash 是同一件事。 手工版由 nc 的 -e 完成 socket/bind/listen/accept/dup2/exec 六个动作，这段代码只是把它用 C 重写了一遍。

代码里的中文注释是为了讲解加的，原文件里只有这一堆系统调用，一句注释都没有——这也是它当年能藏住的原因之一。

看清楚这一点，-e 那一步就不只是练习了——它是这个后门的原型。

dup2(rfd, 0/1/2) 是最关键的一行：把 socket 复制到标准输入、标准输出、标准错误三个位置上。之后 execl("/bin/sh") 启动的 shell，读到的每个字节都来自这根网线，打印的每个字节也都回到这根网线。它一检查 fd 0，发现不是 tty，就按非交互模式跑——不打提示符、不回显输入，但命令照收照执行。这才是连上 6200 之后屏幕一片空白、敲什么却都有反应的原因。

while(1) 外面套 fork()，意味着每来一个连接就开一个子进程，所以 6200 可以同时被好几个人连，各敲各的。

10.4 为什么直接是 root

这是整个漏洞里最要命的一点。

vsftpd 的设计是：用 root 启动，绑完 21 端口、做完认证，再降权到 ftp 用户。降权必须在认证之后——因为要先读 /etc/passwd 和 /etc/shadow 才知道这个用户是谁、密码对不对，而这两个文件只有 root 能读。

而 :) 的检查发生在 vsf_cmdio_get_cmd_and_arg()，也就是读命令的时候——认证还没走完，进程还是 root。

于是时间线变成这样：

不是「提权到 root」，是「还没来得及降权」。 这个区别很重要：它解释了为什么这个后门不需要任何本地条件，也解释了为什么它这么致命——利用者拿到的不是「一个能读文件的账号」，而是整台机器。

10.5 怎么修

按「治标到治本」排：

  1. 升级。2.3.5 及以后没有这段代码。这是唯一彻底的修法，也是当年的处理方式。
  2. 校验下载的东西。源码包发布时带签名和哈希，装之前对一遍。这次事件里，被替换的就是发布方提供下载的那个包，所以「从官网下的就安全」这个假设本身就不成立。
  3. 别把 21 暴露在公网。内部用的 FTP，限制来源网段。这一条挡不住后门，但能挡掉绝大多数扫描器。
  4. 监控非预期监听。6200 不在任何标准服务列表里，一台 FTP 服务器上出现它，本身就该报警。ss -lntp | grep 6200 放进巡检脚本，成本很低。
  5. 日志特征。FTP 日志里出现 USER xxx:) 这种用户名，是最直白的告警信号——正常人不会这么起名字。

第 4、5 条值得多说一句：这个后门的流量特征太明显了，端口固定、触发串固定、用户名里带表情符号。它不是那种需要仔细分析才能发现的高级威胁，问题在于没人去看。

十一、防守视角

前面十节都在讲攻击侧。换到对面，这六步在防守方眼里长什么样：

攻击动作 留下的痕迹 能不能发现
nc -z 扫 1-200 200 次 TCP 握手，绝大多数被拒 能，防火墙/IDS 上是一条整齐的端口序列
抓 banner 一次完整连接，读完就走 较难，和正常访问没区别
发 USER hello:) FTP 日志里一行异常用户名 最容易发现，特征太明显
连 6200 一个不该存在的端口被访问 能，前提是有人在看监听列表

四条里有两条是「只要看就能发现」的。所以这个案例真正的教训不是「vsftpd 有个后门」，而是默认配置 + 从不巡检 = 后门可以躺十年。Metasploitable2 干脆把这个带后门的版本收进镜像，十几年不动，一直是入门课的靶子。

这一篇从头到尾只用了两个工具：nc 和一个 51 行的 Python 脚本。前者 1996 年的，后者一屏就能读完。但走完六步之后，课件里那几个抽象的词——「漏洞」「EXP」「后门」——变成了具体的动作：一行 banner、两行 FTP 文本、一个连上去就能敲的 shell。

笑脸后门最刺人的地方在于，它的利用条件简单到近乎羞辱：:)。两个字节。一个表情符号。

而它之所以能成立，不是因为写代码的人多聪明，是因为从下载到安装，中间没有人核对过那一次哈希。
