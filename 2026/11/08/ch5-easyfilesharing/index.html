Easy File Sharing 远程溢出复现

一、以上 PPT 内容复现。

二、课本 P170 的 7.4 复现。

三、主要步骤截图。

第五章最后有一节实例课，讲的不是方法论，是把一个真实漏洞从头走到尾：装靶机、扫端口、查漏洞、跑脚本。

配套的知识点是 exploit-db——一个公开漏洞库，Kali 里自带副本，searchsploit 就是查它的命令行。这一节练的不是”发现漏洞”，而是已知漏洞的复现流程：拿到目标、确认版本、找到对应 PoC、打出去。

一、实验目的

  1. 在本机部署 Easy File Sharing Web Server，作为远程溢出漏洞靶机
  2. 用 Nmap 扫描识别目标服务与版本
  3. 用 searchsploit 在 exploit-db 中定位对应的利用代码
  4. 用 Python 脚本对目标实施攻击，观察执行结果

二、实验环境

角色 系统 地址 端口
靶机 Windows 11 家庭版 Build 26200 192.168.96.1（VMnet8） 8000（默认 80 亦可）
攻击机 Kali Linux（先 2023.3，后重装为 2026.3） 192.168.96.128 → 192.168.96.130 —

软件由老师提供：efssetup_20181.exe，试用版。

攻击机换过一次。 第一轮用的是旧的 Kali 2023.3（192.168.96.128）；后来为了修 Metasploit 重装了 Kali 2026.3，IP 变成 192.168.96.130。第六节的 msf 命令用的是新地址，前面几节截图里还是旧地址。

靶机就是本机。因为本机同时连着校园网，第一轮启动服务前做过网络隔离，只允许 Kali 访问 8000：

这条规则在重装靶机之后没有再加。实际生效的是安装包自己写入的放行规则（允许任意来源），所以第六节换到 192.168.96.130 之后照样能打。

三、实验步骤

3.1 安装并启动服务

运行 efssetup_20181.exe，一路默认安装，结束后点 Try it! 进入试用版。

主界面里把 Port 从默认的 80 改为 **8000**（课件演示用的也是 8000），然后点 Start。底部状态栏显示 Web Server is online 即启动成功：

验证方式：浏览器访问 http://192.168.96.1:8000，出现登录界面，与课本图 7-12 一致：

试用版单次运行时限为 30 分钟，超时会自动停止服务并弹窗提示，重新启动即可。因此从启动到完成攻击要连续进行。

四、第一次尝试：没打穿

脚本正常执行，payload 全部发出。检查靶机侧：

未观察到计算器弹出，进程也未崩溃。

这个现象说明：溢出没有发生。如果是覆盖成功但跳转地址失效，进程会因异常未被处理而终止；进程能继续正常服务，说明数据没有写到栈上。

进一步验证：直接发送 10000 字节的 HEAD 请求。

服务端照常解析请求、返回 404，进程无异常。当时据此判断”偏移量不适用、版本不匹配”——这个判断后来被推翻了，见下一节。

五、重装之后：两发两中

把靶场卸掉，用安装包的默认配置重装一遍（不改端口、不开任何额外选项），然后原样再打一次：

nmap 先确认服务：

脚本输出和第一次一模一样，还是那两行：

但这次靶机上弹出了计算器。

同时检查靶机侧：

fsws 进程消失、80 端口关闭、桌面上多了一个计算器——这是这个溢出最标准的成功形态：shellcode 被执行了（计算器启动），随后进程因为栈被破坏而崩溃退出。

第一次尝试时进程”既不弹也不崩”，说明请求根本没走到溢出的那行 strcpy；这次崩了，说明数据确实写越界、SEH 链确实被劫持、跳转也确实落到 shellcode 上。

为了确认不是偶然，重启靶场后又打了一次，计算器再次弹出，进程再次崩溃。两发两中。

这一轮和脚本那一轮有个明显区别：脚本的 calc shellcode 一执行，进程立刻崩溃退出（栈被破坏后无法继续）；msf 的 stager 是在进程内加载第二阶段，fsws 进程还活着，80 端口继续服务，会话也是稳定可交互的。同样是 SEH 覆盖，payload 的加载方式不同，后果就不同。

关于 msf 环境

最开始这条走不通，是环境问题：Kali 里 metasploit-framework 的 vendor bundle 内 gem 的 C 扩展按旧版 Ruby 编译，和系统 Ruby 3.3 不兼容，msfconsole 起不来。按顺序试过重装框架、补装 stringio / psych、把 gem 装进 vendor 目录、gem pristine --all、bundle install，全部卡在原生编译这一步（nokogiri 的 openssl 冲突、pcaprub 缺 libpcap、ruby-oci8 需要 Oracle 客户端）。

这类”一堆 gem 报错”的故障，逐个修是修不完的——每个都是独立的环境依赖，修好一个冒出下一个。后来换了一版干净的 Kali，msfconsole 和 msfvenom 直接可用，十分钟就完成了这一步。

七、第一次为什么打不穿

先排除掉几个最像的原因：

怀疑对象 结论 依据
PoC 版本不对 不成立 重装用的是同一个安装包，fsws.exe 仍是 7.2.0.0、构建时间 2015-10-14
老 PoC 打不了新系统 不成立 靶机是 Windows 11 Build 26200，脚本和 msf 模块都能打穿
偏移量算错 不成立 4061 这个偏移一次命中，中间没有改动过
端口 / SSL 配置 不成立 重装后把端口改回 8000、443 照样常驻，两种打法依旧成功
安装状态（试用期） 最可能 旧安装 .ghp 页面全部 404、超长请求毫无反应；重装后全部正常

端口这一条是关键实验。 重装之后把端口改回 8000、SSL 也开着——也就是把第一次那两个”看起来最像”的差异全部还原——结果照样打穿。所以差别不在配置项上，而在那台安装本身的运行状态。

旧安装是 11 月 7 日装的，前后折腾了两天，中间反复重启，还出现过运行时长的限制提示：

EFS 是试用版，超出试用额度后很可能进入一种受限模式：页面还能打开（/ 返回 200），但请求处理被简化了。

这个推断能同时解释当时观察到的三个现象：

  • 4061 字节和 10000 字节的 URI 都被正常返回 404，没有任何异常
  • 5000 字节的 Cookie 送过去，服务器照常返回 200
  • 所有 .ghp 动态页面（/vfolder.ghp、/forum.ghp）都是 404

也就是说，那台服务当时更像一个”只会返回静态页面”的壳，请求根本没走到真正处理逻辑里。这是推断，没有用调试器跟进去验证，但它能解释全部现象，而且重装即可恢复——符合试用软件的常见行为。

第一次给出的三个原因（版本不匹配、系统跨度大、试用版功能受限）里，前两个已经被实验推翻，第三个方向对了但说法不准：不是”功能受限所以入口不存在”，而是整个请求处理被降级了，所以连溢出都进不去。

这大概是这次实验最有用的教训：在怀疑漏洞、偏移、系统之前，先把环境还原到默认状态。 跑了两天、反复重启、改过配置的靶场，和刚装好的靶场不是一回事，前者的所有失败都失去参照价值。

八、小结

  1. 四步流程完整跑通，两种打法都拿到了结果：39009.py 弹出计算器（两发两中），Metasploit 的 easyfilesharing_seh 模块拿到可交互的 meterpreter 会话（80 和 8000 都成功）。课本 7.4 要求的模块路径同样完成了。
  2. “脚本执行成功”不等于”攻击成功”。课件第 5 页的输出只有 Connecting to 和 Done... 两行——脚本只管把包发出去，是否打穿要看目标侧的现象，不能以攻击端的日志作为判断依据。这两行在失败的那次和成功的那次完全一样。
  3. **判断卡在哪一层，靠”进程有没有崩溃”**。崩溃意味着溢出已发生但利用链中断，不崩则说明数据从未越界。这个区分能把排查方向从”换个脚本再试”收敛到具体环节——这次正是靠它确认了第一次压根没进溢出代码。
  4. 同一个漏洞，payload 的加载方式不同，后果也不同。脚本的 calc shellcode 执行完，进程立刻崩溃；msf 的 stager 在进程内加载第二阶段，fsws 还能继续服务、会话也稳定可交互。所以”打没打穿”要看一组现象，不能只看一个信号。
  5. 归因要能通过实验检验。第一次给出的三个原因，前两个被”重装后照打”直接推翻，第三个方向对了但说法不准。连最像的”端口/SSL 是变量”这个猜测，也被改回 8000 后的复测否掉了——看起来最合理的解释，往往一击就破。
  6. 跑久了的靶场和刚装好的不是一回事。试用软件超期后可能悄悄降级（页面照样开，请求处理被简化），表面完全看不出异常。复现失败时，第一步不是换脚本、不是换系统，而是把靶场还原到刚装好的状态。
