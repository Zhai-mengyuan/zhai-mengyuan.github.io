Easy File Sharing 远程溢出复现

一、以上 PPT 内容复现。

二、课本 P170 的 7.4 复现。

三、主要步骤截图。

第五章最后有一节实例课。跟前面不同，这次不是讲方法论，是照着课件把一个真实漏洞从头走到尾：装靶机、扫端口、查漏洞、跑脚本。

课件只有六页，四步动作。但这四步走下来踩了四个坑，还有一个”看起来完成了、其实没打穿”的结局。

一、课件给的是一条既定的路

课件的逻辑很干净：

  1. Windows 靶机装 Easy File Sharing Web Server，这个版本有远程溢出漏洞
  2. 用 Nmap 扫描，发现目标在 8000 端口跑着这个软件
  3. 在 Kali 里用 searchsploit 查它的漏洞
  4. 用 Python 脚本打

配套的知识点是 exploit-db：一个公开漏洞库，Kali 里自带副本，searchsploit 就是查它的命令行。

也就是说，这一节要练的不是”发现漏洞”，而是”已知漏洞的复现流程“——拿到目标、确认版本、找到对应 PoC、打出去。这正是真实渗透里最常见的日常。

二、环境

角色 系统 地址
靶机 Windows 11 家庭版 Build 26200 192.168.96.1（VMnet8）
攻击机 Kali Linux 2023.3 192.168.96.128

靶机就是本机——老师说可以在本机装，但要隔离开。所以先做了一件事：把 8000 端口只对 Kali 开放，其他来源一律拦掉。本机还连着校园网，这个隔离不能省。

软件从同学那里拿的 efssetup_20181.exe，装完点 Try it! 进试用版。

浏览器访问 http://192.168.96.1:8000，能看到和课本图 7-12 一模一样的登录界面：

三、扫描：两个坑

第一次扫，直接失败：

坑一：nmap 先 ping。Windows 防火墙默认不回 ICMP，nmap 判断”主机不在线”，直接跳过扫描。加 -Pn 跳过主机发现：

坑二：端口显示 filtered。第一次加完 -Pn，8000 显示的是 filtered 而不是 open。filtered 的意思是”包被防火墙静默丢弃”——连拒绝都不回。原因是防火墙里还留着一条全阻断规则，它优先于放行规则，把 Kali 的包也一起吃掉了。

这两个坑都指向同一件事：扫描结果不对，先怀疑路径，别怀疑目标。主机在不在、端口开不开，nc -zv 一条命令就能验证，比盯着 nmap 的输出猜要快。

拷出来：

但这里出现了一个矛盾：nmap 和 HTTP 响应头都说版本是 6.9，而这条 PoC 是给 7.2 的。主程序的文件属性里写的又是 7.2.0.0，编译时间 2012 年。

同一份文件，三个来源，两个答案。当时没在意，后来它成了关键。

五、攻击：输出和课件一模一样

原脚本是 Python 2 写的（print "..." 不带括号），Kali 2023 没有 python2。手工改了三处：print 加括号、字符串加 b 前缀变成 bytes、send 换成 sendall（send 不保证一次发完）。

那一刻我以为成了。

六、然后发现靶机没有任何反应

去 Windows 上查：fsws.exe 进程还活着，8000 端口还在监听，没有计算器弹出来。

脚本说 Done，靶机说没事。

这里要搞清楚一件事：SEH 溢出失败有两种完全不同的表现。

现象 含义
进程崩溃，但没执行 shellcode 溢出成功覆盖了返回地址，跳转失效或被 SEHOP 拦
进程毫无反应，继续正常服务 溢出根本没发生，数据没写到栈上

这次是第二种。

于是做了个测试：直接发一万个 A 过去。

一万个 A 砸过去，服务端照样解析请求、照样返回 404，进程一点事没有。

如果只是偏移量不对（4061 这个数是 PoC 作者在自己那版二进制上量的），那么 4061 个 A 就该把栈踩穿、进程崩溃。它连崩都不崩，说明这条代码路径上的缓冲区根本没有那么小。

“偏移不对”和”没有缓冲区”是两回事，这次是后者。

七、试用版的两道限制

试到一半，EFS 自己停了，弹出一个框：

试用版单次只能跑 30 分钟。也就是说，从启动服务到打完攻击，必须在这半小时内完成。这不是技术问题，但如果实验做到一半服务突然消失，很容易误判成”被攻击打挂了”。

后来还有第二个限制：这个安装包里所有 .ghp 动态页面（论坛、虚拟文件夹）全是 404。而 6.9 专用的那条 PoC（37951.py，UserID 溢出）恰恰要求访问 /vfolder.ghp——页面不存在，payload 就没有落点。

两个限制叠在一起：请求行打不崩、动态页面打不着，三条公开 PoC 换着打也没能打穿。

八、课本 7.4 那条没能走完

课本 P170 的 7.4 是用 Metasploit 打同一个软件：

成功的话会拿到 Meterpreter session 1 opened，也就是一个反弹回来的控制通道。

这条没能完成，卡在环境上：msf 的 vendor bundle 里那些 gem 的 C 扩展是按老版本 Ruby 编译的，而系统现在的 Ruby 是 3.3，两者对不上，全部加载失败。修的过程是这样的：

尝试 结果
apt install --reinstall metasploit-framework 缺少 stringio、psych gem
gem install stringio psych 装上了，但 Bundler 的 GEM_PATH 看不到
装进 vendor 目录 又冒出 31 个 gem 的 missing extensions
gem pristine --all 修了一部分，卡在 ffi 平台错误
bundle install nokogiri 编译失败（openssl 版本冲突）、pcaprub 缺 libpcap、ruby-oci8 要 Oracle 客户端

最后停在「只剩 3 个 gem 装不上」。这不是配置问题，是这套 Ruby 环境已经乱了——继续修要重装 Ruby 和 msf，成本已经超过收益。

这一项如实记为未完成。 顺带说一句：那个模块的 target 写死是 Easy File Sharing 7.2 HTTP，就算 msf 起来了，用它打 6.9 大概率也是空炮，和前面 39009 的结局一样。

九、这一节学到了什么

按”完成任务”算，只做了一半：四步流程走完、截图齐全，但最后一击没打穿。

按”理解漏洞”算，收获反而在后面那半天：

第一，”脚本执行成功”不等于”攻击成功”。 课件第 5 页那张图上的输出只有 Connecting to 和 Done... 两行——脚本把包发出去就算完事，打没打穿它不知道，也管不着。真实渗透里，判断成败的永远是目标侧的现象，不是攻击端的日志。

第二，判断卡在哪一层，靠的是”进程崩没崩”。 这一条把六次失败的排查从”再换个脚本试试”变成了有方向的诊断：崩了是偏移问题，不崩是根本没溢出。

第三，版本号不能只信一个来源。 文件属性可以改，HTTP 头可能没跟着更新，nmap 指纹靠特征匹配。这次三个来源两个答案，恰好看出了这个包不对劲。

第四，靶场环境和真实环境差得远。 课件那台靶机是 2019 年的旧 Windows（nmap 里开着 135 RPC 和 139 netbios），我这是 2026 年的 Win11 Build 26200。一个 2012 年编译的 32 位程序跑在上面，栈布局、异常分发、CRT 行为全都不是当年那个样子了。这类老 PoC 打不穿，往往不是手法问题，是时间问题。

要真打穿，只有两条路：换一台 XP 或 Win7 的靶机，或者用调试器实测这一版的偏移量，自己写 PoC——后者其实才是缓冲区溢出这一章真正想教的东西。
