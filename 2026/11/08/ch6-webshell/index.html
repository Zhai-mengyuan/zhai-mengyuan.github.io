一句话木马：从 URL 到服务器控制台

二、目标网站写入一句话木马，利用蚁剑连接并控制目标网站，主要步骤截图。

第五章结尾那个 6200 端口，本质上已经是一个后门了：连上去就能敲命令。但它有个明显的短板——那个端口是漏洞自带的，不是攻击者放的。换一台没有 vsftpd 漏洞的机器，这条路就断了。

第六章讲的是另一种控制方式：自己把后门送进去。

一、四种「shell」，别混着叫

课件第 6 页列了四个词，它们经常被混用，但指的东西完全不同：

名词 是什么 跑在哪
Shell 命令解析器，比如 bash、cmd.exe 目标系统的进程里
Shellcode 一段十六进制机器码，利用漏洞时塞进内存执行 目标进程的栈/堆里
Webshell 一个网页后门脚本，上传到网站后通过 HTTP 调用 Web 服务器的脚本引擎里
一句话木马 Webshell 的极简形态，只有一行代码 同上

第五章那个 vsftpd 后门，是直接改在源码里的——攻击者替换了发布包，多塞了一个函数进去，程序一启动就带着它跑。它既不是溢出利用，也不是运行时注入的 shellcode。

这次要做的是一句话木马，属于 webshell：不占端口、不起新进程，就是网站目录下的一个 .php 文件，靠正常的 HTTP 请求活着。

这也是它难被发现的原因：从流量上看，它和一个普通网页请求没有区别。

五、system 型和 eval 型：一字之差，两个入口

这里有个值得单独写的细节。

最开始我用的是 shell.php（system 型），蚁剑怎么连都失败，提示「返回数据为空」，换三种编码器都不行。后来把木马换成：

存成 shell2.php，一次就连上了。

原因在两者接收的东西不同：

木马类型 接收什么 例子
system() shell 命令 whoami、ls -la
eval() PHP 代码 echo "abc";、system("whoami");

而蚁剑的工作方式是：把每一项操作翻译成 PHP 代码，再发给木马。它的文件管理功能发的是 @ini_set(...)、base64_decode(...) 这类 PHP 语句，执行结果再用 echo 打回来。

system() 拿到这些 PHP 代码，会当成 shell 命令去执行——echo 在 shell 里确实存在，但 base64_decode(...) 就完全不是命令了，执行失败，返回空。

所以：

  • 手工用 curl 打：system 型最直接，一条 URL 就能跑命令
  • 用蚁剑这类工具：必须 eval 型，因为它发的是代码不是命令

同为一句话木马，用途不同，写法就不同。这个区别在课件里没写，但配工具时一定会撞上。

六、为什么这种后门特别难查

一句话木马只有 30 字节，可以藏在任何 .php 文件里，甚至拼接到一张图片的尾部再配合解析漏洞使用。它的请求也完全是正常的 HTTP：

防火墙看到的是一个普通的动态页面请求，日志里只有一条 200。没有异常端口、没有异常协议、没有可疑进程。

对比第五章那个 6200 后门——它至少开着一个不该存在的端口，netstat 一扫就露。而 webshell 混在正常的 Web 流量里，发现它靠的是文件完整性检查和日志审计，不是端口扫描。

这也是课件把 webshell 归到“远程控制”而不是“漏洞利用”里的原因：它不是打进去的那一下，是打进去之后留下来长期待着的那部分，也就是权限维持。

七、当时卡住的那条，后来补上了

写这篇的时候，课件第 9–10 页那条（msfvenom 生成被控端、msfconsole 开监听、让靶机回连）还没做成：Kali 里 Metasploit 起不来，vendor bundle 里的 gem 是按旧版 Ruby 编译的 C 扩展，和系统的 Ruby 3.3 不兼容。

后来重装了一版干净的 Kali，这条通了，完整过程写在另一篇里：《反向连接：从 msfvenom 到沙箱判定》。

顺手记下当时的判断，以后再遇到类似情况能省点时间：这类”一堆 gem 报错”的故障，逐个修是修不完的。ruby-oci8 要 Oracle 客户端、nokogiri 要特定版本的 openssl、pcaprub 要 libpcap——每个都是独立的环境依赖，修好一个冒出下一个。与其在旧环境里打补丁，不如直接换一版干净的系统，半小时的事。

八、小结

  1. 一句话木马的本质是“参数 → 执行”。它不依赖任何漏洞，依赖的是网站允许用户上传文件这个前提。一旦文件落地，URL 就成了命令入口。
  2. system 和 eval 是两种入口：前者收 shell 命令，后者收 PHP 代码。手工打用前者，配蚁剑这类工具必须用后者——这个区别是这次卡住又绕回来的地方。
  3. 执行身份是 Web 服务的身份，不是系统用户。www-data 权限有限，但足以读配置、改代码、横向找提权点。
  4. 它的隐蔽性来自“正常”：不带端口、不带协议特征，混在 HTTP 流量里。防守端靠文件监控和日志审计，扫描器扫不出来。
  5. 远程控制有两种形态：一种是漏洞自带的后门（第五章的 6200），一种是攻击者自己放的后门（这一章的 webshell）。前者靠打补丁解决，后者靠“别让不该出现在网站目录里的文件出现”解决。
